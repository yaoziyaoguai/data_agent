Data Agent：语义、记忆与召回

从一张表的解释，到一次有依据的查询。

source2026-10-06 · 语义协作增量 · Datasight mock

共享语义回答“数据是什么、应该怎样算”。个人记忆回答“这个用户长期有什么偏好和纠错”。Pi 会话上下文回答“这段对话已经聊到哪里”。

“召回”就是从存储中找出本次可能需要的材料。找到之后，还要读原文、核对有效性，再决定怎样用。

A

先分清：项目里有哪三种“记住”？

这里把你说的“整体记忆”对应为共享知识库。它保存同一空间内可共享的业务知识。具体能看什么，仍由权限决定。

类别 记住什么 谁可以复用 主要负责者
共享语义，也就是共享业务知识 表、字段、指标、关联、术语、业务文档 同一空间内有权限的人 Rust 语义模块
个人长期记忆 本人的默认偏好、纠错、适用范围与例外 同一用户、同一空间，可跨对话 Mem0 提取与检索；Rust 管正式版本
当前对话上下文 消息、工具历史、已明确条件、分析任务 继续这段有权访问的对话时使用 Pi SDK 与 Rust 任务记录

共享知识与个人记忆有明确归属。 用户聊天中的一句纠错，先属于本人；公共定义需要走语义维护流程。

整个产品怎样工作

  • React 展示聊天、SQL、结果、语义页和个人积累。
  • Pi SDK 运行唯一的 Agent 循环，使用 DeepSeek Flash。
  • Pi 按问题选择工具，可以补查、追问和修改 SQL。
  • Rust 校验权限、版本、预算和具体 SQL 的确认状态。
  • 当前查询平台使用可执行合成数据；真实平台通过适配器接入。

这张图只表示用户过程。调查中的工具顺序由 Pi 判断，用户也能在执行前继续补充。

依据：架构职责、Agent 当前行为约定。

B

语义怎样从原始资料构建出来？

语义层要把“有这些字段”补成“这些数据该怎样使用”。 预填页面是维护入口，背后保存的是有来源、有版本的知识。

页面维护哪些内容

内容 需要解释的问题 合成零售例子
表 一行代表什么？主键是什么？哪些时间可用？ 一行是一个订单行，主键是订单号加行号
字段 含义、单位、取值、空值和边界是什么？ paid_amount_cents 是当前行的成功支付金额，单位为分
指标及计算 SQL 怎么算？按什么时间？有哪些过滤和维度？ 支付归属净收入＝付款减退款，按付款月统计
查询关联 怎样连接？会不会把金额重复计算？ 客户标签是一对多关系，直接连接可能放大金额
术语与规则 业务叫法和例外怎样解释？ “退款率”仍需明确用订单数还是金额作分母
文档、章节和主题 哪些内容需要完整说明？ 一篇文档解释退款归属，同时关联表、字段和指标

预填的实际过程

平台资料先保存快照，结构事实可直接预填。模型再结合 DDL、加工 SQL、血缘和业务文档解释含义。当前模型预填分为分析、依据复核两次调用。

关联文档保存在知识库，按版本加入分析材料。只保存链接但读不到正文时，系统保留“正文不可用”的缺口。

同一个条目保留三类内容

层次 保存的内容 更新规则
来源事实 原始字段类型、注释、SQL、来源版本和引用 同步新来源，保留出处
模型建议 对含义、单位、边界的解释及证据、缺口 重新分析可以更新建议
人工覆盖 数据开发填写的值、修改人和操作记录 后续预填保留人工值

页面采用的值由这三层合成。人工覆盖优先；没有人工值时，可使用来源事实或模型建议。模型建议仍标记未验证，不能显示成“人工已确认”。

来源变化时，系统更新版本并标记需要复核。人工内容会保留，新建议也能查看。

两个容易误判的地方

SQL 可以证明“代码做了什么”。收入归属等业务含义，还需要业务依据。

血缘说明“数据从哪里来”。查询能否直接 JOIN，还要核对关联键和一对多关系。

引用逐字匹配，只能证明引用存在。模型的业务推导仍可能有错。

依据：语义条目与人工保护、模型预填实现、两阶段处理。

C

共享语义的原文和索引分别存在哪里？

MySQL 保存正式内容，Milvus 帮助找相关内容。 模型把文本转成一串数字，这个过程叫 embedding，也就是向量化。

保存位置 实际内容 用途
MySQL 来源记录 平台快照、来源头和采集版本 能追溯分析所用的原始资料
MySQL 共享知识 对象、不可变版本、条目、文档、引用与人工覆盖 编辑、读取和核对正式定义
MySQL 词法检索副本 当前知识的可检索文字 按名称或关键词找候选
MySQL 索引任务与调用回执 索引进度、原预算、成功向量和使用量 失败恢复、重建及费用核对
Milvus 共享集合 语义片段的向量、对象 ID、版本、空间及片段文字 按意思相近查找候选

例如，“净收入”和“扣完退款还剩多少”用词不同。向量模型有机会把它们放得较近。这个相似度帮助定位资料，不能决定业务定义是否正确。

当前实现的几个具体细节

  • 向量模型是百炼 qwen3.7-text-embedding，每个向量有 1024 维。
  • 共享知识和个人记忆使用两个独立的 Milvus 集合。
  • 个人集合内再按用户与空间隔离，无需为每个人另建数据库。
  • 共享语义按 360 字符切片，相邻片段重叠 80 字符。
  • 每对象最多 128 个片段；超过范围会标记覆盖不足。
  • 当前共享向量索引跳过原始 DDL、加工 SQL 条目。
  • 原始 DDL 和加工 SQL 仍保留，可由工具回源阅读。

语义更新后，Worker 更新对应版本的索引。新索引尚未完成时，正式文字依然存在。检索会说明索引状态，旧向量也不能代替新的正式版本。

这里的 MySQL 是应用存储。 用户要查询的业务明细属于数据平台；当前合成平台用 SQLite 执行样例 SQL。

依据：共享索引切片、调用与恢复设计、本地运行说明。

D

一条个人记忆怎样保存？

假设用户说：“以后我的收入分析默认只看 web 渠道；明确说别的渠道时，以当次要求为准。” 这是一条教学示例，用来说明保存过程。

Pi 判断需要长期保存，先查本人已有记忆。Rust 核对引用的原话、归属和依赖，再交给 Mem0 提取。

为什么既用 Mem0，又写 MySQL

Mem0 从用户原话中提取候选。Rust 保存经校验的正式版本，并负责页面编辑、启停、删除和用户隔离。

Mem0 在提取时可能已生成向量。此时状态是 pending，查询不能采用。MySQL 保存成功后，Worker 再把对应候选提交为 ready。

所以，要分别看“正式记忆已保存”和“索引已就绪”。MySQL 保存失败，不能告诉用户已经记住；索引暂时失败，也不能丢掉正式正文。

位置 个人记忆相关数据
MySQL 用户、空间、正文、原话、范围、版本、依赖和启停状态
Milvus 个人集合 Mem0 候选及已提交记忆的向量、资产 ID 与版本
Mem0 本地 SQLite SDK 历史、提取回执、资产与向量的映射、操作恢复记录

哪些内容会长期保存

  • 明确说“记住”“以后默认”“修改之前的偏好”时，走保存或修订流程。
  • “这次只看 app”属于当次条件，不自动写成长久偏好。
  • 自动记忆的正文与适用范围使用同一份 Mem0 最终文本。
  • 原话单独保留，便于追溯范围和例外。
  • 页面手工编辑直接保存用户填写的正文，再建立索引。
  • 手工正文不再交给 Mem0 改写，避免改变用户原意。

个人 Skill 也存为个人资产，表示可复用的方法。当前由页面维护并明确选择，Agent 采用本对话已选的有效版本。

依据：Mem0 提取、提交与存储、Rust 记忆用例。

E

语义召回：怎样从很多表里找出本次需要的知识？

以“查 2026 年 1 月净收入”为例。Agent 需要找到指标、表、金额字段、时间口径和相关文档。

三条查找通道合起来使用

通道 适合什么问题 当前做法
精确匹配 用户知道表名、对象名或 ID 精确名称优先
关键词 问题与资料有相同词语 查正式内容及词法检索副本
向量相似 用户换了一种说法 Qwen 生成问句向量，Milvus 找相近片段

回源就是拿着候选 ID，回到 MySQL 读当前正式记录。系统核对空间权限、启停状态、对象版本和来源版本。查到了旧版本或失效来源，就不能把它当作当前依据。

排名会综合关键词与向量的名次。结果还尽量包含表、字段、指标、文档等不同类型，并补入少量关联对象。当前没有另调一个大模型逐项打分。

search_knowledge 先返回目录和摘录。Pi 可再用 read_knowledge 分段读正文，用 read_source 读原始资料。能定位到文档，还不等于已经读懂完整口径。

检索不完整时怎样处理

向量服务不可用时，系统明确报告降级，保留精确与关键词通道。候选扫描或索引覆盖有限时，会返回覆盖状态。

因此，空结果只能表示本次没找到。Agent 可以缩小业务范围、换名称、按已知 ID 读取，或询问用户。

依据：三路合并与回源、排名规则、受控知识工具。

F

个人记忆和对话历史又怎样找回来？

个人记忆与共享语义分别检索，最后一起供本轮判断。 同一个知识工具可以返回两类结果，返回字段仍然分开。

个人记忆的两次使用机会

新一轮启动时： 若本人有有效记忆，Rust 用本次问题调用 Mem0。它先挑相关项，再从正式目录补充未进入索引的有效项。当前最多准备 20 条记忆摘要，然后按整体输入大小裁剪。

Agent 调查中： Pi 调用 search_knowledge 时，也能取得个人记忆候选。需要更多内容，可分页查看本人目录，再按版本读取正文。

Mem0 搜索限定当前用户、空间及 ready 状态。侧车最多取得 200 个候选，并核对其映射。Rust 还会检查正式资产的版本、状态和依赖。

Mem0 暂不可用时，系统回退到本人正式目录，并报告回退状态。停用记忆后，后续采用以 MySQL 状态为准，不必等待旧向量清理完成。

对话上下文走另一条路

问题 个人长期记忆 Pi 对话上下文
保存什么 跨对话可复用的偏好、纠错 这段对话的消息、工具调用与压缩记录
主体内容在哪里 MySQL 正式资产，Milvus 提供检索 Pi 原生 JSONL 会话文件
怎样恢复 Mem0 搜索，再回源核对 Pi SDK 恢复同一会话及已提交的位置
历史太长怎么办 选相关摘要，完整内容按需补读 使用 Pi 原生上下文压缩
Rust 另外保存什么 归属、版本、依赖和索引任务 对话与任务状态、查询、精确检查点引用

同一对话可以持续多轮、包含多个任务。模型本轮看到的是有效历史、必要摘要和工具补读内容，不会一次装入所有存储。

语义改版、记忆停用或权限变化后，Rust 复核此前使用的依据。必要时为新一轮重建上下文；恢复中断任务时也不能继续采用失效资料。

依据：启动时召回个人记忆、Mem0 搜索过滤、Pi 会话持久化。

G

用一个完整例子，把三类内容放到一起

以下基于仓库的虚构零售样例。个人偏好和提问用于教学，不是本页发起的实时查询结果。

三类材料分别贡献什么

材料 已有内容 本轮用途
共享语义 一行是一个订单行；金额单位为分 避免把行数当订单数，或把分当元
共享指标 净收入＝付款减退款；按 paid_at 归属月份 决定公式、时间列及退款归属
共享规则 默认排除测试交易；退款累计到样例快照 决定过滤，并解释数据截止范围
小陈的个人记忆 收入分析默认只看 web；当次明确条件优先 用户没指定渠道时，补上默认渠道
本次对话 “查 2026 年 1 月净收入” 固定本次期间和目标

Agent 应解释采用的口径，展示 SQL 草稿，等待用户确认。这个样例的快照截止于 2026 年 2 月 4 日 00:00 UTC。

如果用户改口，会改变哪里

用户接着说 当次任务 个人记忆 共享语义
“这次改成 app” 生成 app 条件的新 SQL 版本 仍保留默认 web 不变
“以后默认改成 app” 按当前明确目标处理 Mem0 提取后修订本人记忆 不变
“再按天拆开” 沿用当前任务并修改分组 不自动保存新的长期偏好 仍按原指标口径
另一位用户问同一问题 使用对方本人的条件 不取得小陈的偏好 可读取对方有权限的共享定义
“这张表的金额其实是元” 先查来源，冲突时澄清 可保留本人的待核实纠错 有权维护者核实后修改公共版本

“这次改成 app”会使旧 SQL 草稿失效。执行必须对应用户后来确认的具体版本。

A 纠错，B 是表负责人：已确认的新规则

A 看了 SQL 后指出：“金额单位是分，展示成元要除以 100。”B 是该表的语义负责人。

接受后编辑保存才生效

表维护者负责该表语义。超级维护者可维护本系统全部表的共享语义。

A 可以提交纠错建议。B 可以驳回，或接受后核对、编辑并保存。

只有正式保存才改变共享语义。接受建议表示准备修改。

两套权限各管什么

权限 决定什么 边界
Data Agent 内部语义权限 谁能改哪张表的语义、处理哪些建议 表负责人维护负责范围；超级维护者维护全部表
Datasight 数据权限 谁能读平台资料、查询数据和执行 SQL 继续由平台校验，系统角色不会扩大它
本人记录的访问范围 谁能读聊天、个人记忆和 Skill 语义维护角色不能读取他人的私人记录

即使 B 有语义维护权，核验时执行 SQL 仍需平台权限与用户确认。反过来，A 有数据查询权，也不能直接修改共享语义。

录入人和最后修改人分别记录。表负责人来自 Datasight 最近一次同步；共用指标和文档独立指定负责人。

纠错怎样成为共享改进

状态 A 能看到什么 大家共用的语义
本人草稿 自己整理的建议 保持原版本
已提交待处理 提交内容与待处理状态 保持原版本；不参与共享召回
已驳回 处理人和理由 保持原版本
已接受待修改 已接受，负责人准备修订 保持原版本
正式保存成功 实际修改内容和生效版本 新版本生效，索引异步更新

A 的本次查询不必等待 B 处理。A 的聊天全文、查询结果与 Mem0 个人记忆不会随建议开放；只共享明确提交的修改与依据。

保存时，Rust 重查当前维护权限、建议修订和语义基版本。别人已经改过时，先显示差异再核对，不能用旧建议覆盖新内容。

当前程序到了哪一步

当前能力 实际状态
修订本次 SQL 已有；修订后等待用户确认新版本
本人纠错记忆 已有；明确可复用纠错按原规则保存，未核实内容作查证线索
本人语义建议 已有；Pi 可保存目标、基版本、建议值、理由和依据
负责人处理建议 页面先显式提交，再由负责人接受、核对编辑并保存；旧本人采用 API 保留逐对象权限校验
逐表负责人、超级维护者 已接入；表负责人来自平台同步，超级维护者由可信配置指定
A 提交给 B，B 接受或驳回 已接入；私人草稿显式提交后，B 可接受或驳回

当前没有把每一次聊天纠错都自动登记为建议的程序规则。未来也应区分一次性条件、个人偏好与共享语义错误。

旧私人建议保留原来的私人范围。跨表共用指标和文档由超级维护者独立指定负责人，引用它们的表负责人可以提出建议；引用关系不授予编辑权。

本次明确条件优先于长期偏好。共享定义发生冲突时，Agent 要解释或澄清，并核对来源。

依据：合成业务说明、当前本人建议实现、当前演示权限、已确认的权限与纠错设计。

H

最后记住：哪里靠模型，哪里靠程序？

工作 当前由谁负责 为什么这样分
理解业务问题、选工具、追问、生成 SQL Pi SDK 运行 DeepSeek Flash 给 Agent 调查和判断空间
解释原始资料，补充语义建议 DeepSeek Flash；Rust 核验并保存 附上依据、缺口与版本，保留人工修改
