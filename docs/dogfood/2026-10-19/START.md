# 执行顺序与完成标准

## 1. 先确认执行的是本包

读取仓库 `AGENTS.md`、`docs/CURRENT.md` 的 frontmatter 与最新段落，以及本包 `manifest.json`；历史记录按需检索，不一次加载整部历史。记录实际 Git commit、工作树变化、Pi 版本、模型/思考档、检索与记忆模式、运行目录和数据源指纹。代码变化后将新批次单独记录，不能把跨版本尝试合成一次通过。

本包 160 项全部默认 `not_run`。旧报告仅用于定位回归风险。当前网页能打开、旧 14 组工程通过和旧 120 项报告，都不能替代本次结果。

## 2. 权限、费用和数据范围

准备资料不等于执行收费试用的授权。执行会话中的用户指令、明确采用的执行 prompt 和现有配置决定权限；不要仅凭本文件给自己新增付费或运维权限。已有授权清楚时继续，不重复询问。

真实模型按当前正常请求规则运行：每消息最多 24 次，连续临时失败 3 次停止，摘要、重试、恢复和结果唤醒沿原 scope。不要另造默认总时长/总费用门槛，也不要修改原 profile 扩额。有限 trial 的旧累计上限和到期必须保持；不复制有限 trial 到新库或换 ID 绕过限制。

只使用合成资料。`reference/`、完整试用手册、场景预期、判分、运行结果和源码审计结论只给操作者；不能上传为共享知识、个人记忆、Skill、公共查询案例或塞进产品 Agent 的用户问题。`fixtures/` 中标明用于输入的合成正文、SQL和方法模板可以按场景采用。

凭据仅在本机按任务需要读取/使用，不打印、不截屏、不写入结果或 ZIP。不要采集完整私密思考；模型切换只记录是否隔离、公开文本与工具身份是否保留。

## 3. 环境前置检查

按 `environment.template.json` 写本轮 `.local/dogfood-runs/<run_id>/environment.json`，从 27173 现有入口做只读检查。不要把默认 5173 或 mock 回复当真实模型。确认 API/Worker/平台使用 `docs/sources/analysis`；冻结快照截至 2026-04-04 00:00 UTC，不含该时刻。

在线核对 Alice/Bob/Carol 的实际最高角色、表归属和平台权限。准备时仅有 Alice/Bob 启动证据，Carol 不能假设存在；Alice 代做编辑只能证明超级维护路径，不能证明非超级负责人边界。混合检索、Pro、第二空间、大目录、长查询等待等各有独立前提。

若环境不具备某一能力，写 `blocked_environment`，完成其他可做项目；不要删案例、变更预期或全部停工。没有费用/运维授权时，用 `blocked_authorization` 记录受影响项目，继续无需该授权的项目。

## 4. 建立本轮记录

复制 `records/results-template.json` 到 `.local/dogfood-runs/<run_id>/results.json`。`run_id` 用新的可辨识名称；`run_prefix` 使用 `DF1019_<run_id>`。替换场景消息中这个命名前缀，保留原业务 SQL 和独立数值。

`{{paste_full_january_sql_here}}` 必须替换为 R04 实际前史生成的完整 SQL。不能把占位符原样发给产品。创建对象使用本轮前缀，并记录 ID、owner、version。已有基线资料/用户资产不能为凑前置条件而被覆盖。

结果按 `case_id + attempt_id` 追加。记录原始输入、实际可见答复、最终 SQL/参数、task/query/result/report/asset ID、关键工具参数/回执、截图/下载和结论理由。保留失败；不覆盖旧 attempt。字段定义和评分见 `reference/GRADING.md`。

## 5. 先跑代表样本，再扩展

先执行 B02、B03→B04→B05、B07，核对检索、未授权不执行、明确授权后的实际结果，以及真实澄清。这个小样用于发现环境接错或执行方式不适配，不用于宣布整体质量通过。

真实模型与平台路径正常且本轮已授权批量时，继续下面各批；不需再索取重复批准。若模型来源、材料范围、成本模式或授权与预期不一致，停止受影响操作，留下证据并明确需用户决定的差异。纯模型回答失败则记录，不无限改提示重跑。

## 6. 建议批次与顺序

| 批次 | 主要场景 | 执行环境 |
| --- | --- | --- |
| 页面与查询 | B01–B33，R01–R09，R18 | 只读冒烟可用现有环境；完整写入在本轮沙箱 |
| 维护和协作 | C01–C22、A01–A08、X01–X10，R07/R08 | 三角色与归属已核对的隔离环境；先 C06，再 C17/C19 |
| 记忆和方法 | M01–M20 | 独立账号；涉及显式依赖先准备 C06/M13，再 C21 |
| 分析成果 | B34–B41，Z01–Z04、Z09、Z13 | 同一连续会话，保留原查询和结果引用 |
| 场景串联 | Z05–Z08、Z10–Z12、Z14–Z16 | 按 `depends_on` 与对象条件准备，不按 ID 机械排序 |
| 工程边界 | E01–E19，R05/R10–R17/R19–R24 | 串行隔离协议/合成专项；与真实模型评分分开 |

`depends_on` 表示需要前序产物/状态，**不要求前序整体必须 pass**。例如某依赖失败但必要对象已正确创建时，可注明前提并继续；前提确实缺失才 blocked。不能把 API 代造的产物伪装成前序 UI 或模型成功。

新场景与旧场景可以共用同一真实轨迹以节约调用，前提是输入、前提和每项断言确实全部覆盖，并为各项列出对应证据。业务变体、近似 SQL、只完成一半的流程和旧版本记录不能共用为通过依据。

## 7. 浏览器与 API 怎样分工

用户入口从 UI 走：导航、编辑、选方法、聊天授权、取消、下载、报告与重开都留下界面证据。API/SQL 仅用于已授权的隔离环境准备、独立参考、观察持久状态和工程边界。不能靠直接写库或工具 API 补做产品 Agent 没完成的步骤，再宣布 UI/模型通过。

涉及取消、超时、未知、源版本变化、索引丢失、撤权、服务中断和预算竞争，只在隔离环境故障注入；原 unknown 保留稳定身份、预留和历史，不盲目重做。不停止用户当前环境。

## 8. 串行、分派与断点

多个执行 Agent 只有在用户明确安排时才分派。每个 Agent 有独立 `run_id`、记录文件和可写对象；同一个账号的记忆、同一来源版本、公共方法、负责人变更和故障注入不能并行相互覆盖。需要并行时分别使用独立数据库/runtime；共享 MySQL 集成检查串行，不在检查中重建 API/Worker 二进制。

每完成一个场景就保存结果；每批结束写一次 `HANDOFF.md`。额度耗尽或被中断时，列出最后确认的步骤、在途与 unknown、待核对回执、下一步，保留浏览器、服务和账本必要状态。下一 Agent 从已保存 checkpoint 接续，不重跑已完成批次。

## 9. 最终报告

160 项逐项有状态，状态之和必须为 160。分列 pass、fail、partial、blocked_environment、blocked_authorization、inconclusive、not_run；不要把这些合并成“全部完成”。报告真实模型/UI/协议/平台适配的实际证据类型。

问题按同一根因合并，但保留所有受影响 case_id 和失败尝试。最少提供一个可复现问题的原话、实际版本、操作步骤、期望出处、实际结果、用户影响、证据路径及置信程度。执行任务只试用和记录；不改产品代码、不提交推送、不调试用答案。修复留给后续审计。
