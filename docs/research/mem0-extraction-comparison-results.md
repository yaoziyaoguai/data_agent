# 原方案与 Mem0：原始消息提取及跨对话使用对比

**本轮正常场景的完整成功率相同：原方案 16/18（88.9%），Mem0 16/18（88.9%）。** Mem0 的记忆管理为 17/18、SQL 探针为 24/24，分别高于原方案的 16/18、22/24；但只有九类情境、每类两次，尚不能证明稳定优势。

建议保留当前 MVP 的正式记忆方案，保留已验证的 Mem0 实验接缝。此次没有证明自研记忆优于 Mem0，也不足以支持立即替换。下一步更直接的改进点是保存工具的错误反馈：三个正常保存失败都反复修改 scope，却一直没有修正被截短的 instruction_quote。

## 这次真正比较什么

| 部分 | 原方案 A | Mem0 方案 B |
| --- | --- | --- |
| 决定是否记住、修订或忘掉 | Pi SDK 中的 DeepSeek Flash | 相同的 Pi SDK 与 Flash |
| 整理记忆正文 | Pi Agent 根据原始消息编写 | Mem0 直接读取完整原始消息和本次原文引用，提取正文 |
| 正式保存 | Rust 校验后写入 MySQL | Mem0 正文经同一个 Rust 入口校验后写入 MySQL |
| 后续查找 | 现有个人资产目录和检索 | Mem0 的 Milvus 索引检索，回源核对正式状态和版本 |
| 对话续接、上下文与工具循环 | Pi SDK | 相同 Pi SDK |

MySQL 保存用户所属、正式正文、来源、状态和版本，便于修改、停用及权限核验。Mem0 提取发生在正式保存之前。其候选向量存在本地独立 Milvus 集合，历史存在独立 SQLite。未提交的候选在检索排序前被排除；提取失败不回退成 Pi 正文并宣称成功。正式保存后的索引提交失败会明确降级到正式个人资产目录。

本次保留 Pi 对保存时机和范围的判断。它测试受控个人记忆的提取和复用，没有测试任意聊天自动建立长期记忆，也没有把公共口径交给个人记忆覆盖。

## 已修复的问题

- 产品来源校验：完整引用自身带结束符且后面还有另一句话时，不再误拒；换行仍作为句子边界。保留对裁去否定前缀、临时后缀的拒绝检查。
- 评分：长期默认中说明“当次要求 app 时覆盖”不再因为出现 app 而误判；核对资产身份、版本、正文、来源和范围是否保持，再检查本次与后续 SQL。
- 实验接缝：每个 SDK 工具调用拥有独立提取身份，三条工具请求路径复用同一正文；同一候选不得归属两个正式资产。
- 实验检索：提交标记在 Milvus 检索排序前过滤，防止失败候选挤占有效结果。正式版本和状态仍回源核验。

初次小样运行期间新增审计脚本，冻结检查因此失败，证据保留。随后冻结小样完成 4 组合、8 条消息、50 次 Agent 调用；接入、候选过滤、参数重放和正式正文经独立复核。小样原方案有一次未按工具要求引用完整指令，未保存偏好，未调整题目或消除该内容失败。

## 固定测量口径

本轮使用真实 DeepSeek、真实 embedding API、真实 Mem0 和 Milvus；数据平台使用项目现有的可执行合成 mock，未接入真实 Datasight。

- 9 类正常场景：跨对话、修订、临时覆盖、混合意图、停用、仅本次、金额单位、两个偏好、未核实纠错。
- 3 类故障：Mem0 提取失败、MySQL 保存失败、正式保存后的 Mem0 索引提交失败。故障处理单列，B 专属故障的 A 组只作无故障参照。
- 每个场景每组两次，全新数据库与集合。共 48 组合；正常成功率每组分母 18。两条轮次链并发、轮次内 A/B 顺序交替，共用全局持久预算边界。
- 输入、独立答案、源码和模型配置事先冻结；失败、超时和缺失不补抽。记忆含义、最终解释由独立审查者判断；SQL 依据独立数据及变体执行核算。
- 两组均为 DeepSeek Flash high。Mem0 2.2.1 提取为 Flash 关闭思考；embedding 为百炼 qwen3.7-text-embedding、1024 维。

## 正常场景结果

| 指标 | 原方案 A | Mem0 B |
| --- | ---: | ---: |
| 完整场景成功（保存/管理、SQL和解释全部正确） | 16/18，88.9% | 16/18，88.9% |
| 记忆保存、修订、停用及临时隔离正确 | 16/18，88.9% | 17/18，94.4% |
| SQL 探针正确 | 22/24，91.7% | 24/24，100% |
| 第一轮完整成功 | 8/9 | 7/9 |
| 第二轮完整成功 | 8/9 | 9/9 |

18 对成对结果中，14 对都成功、2 对仅原方案成功、2 对仅 Mem0 成功。重复的是相同九类问题，不能当成18种独立业务问题。Mem0两轮7/9与9/9的波动也说明不宜从少数成功差异推断长期优势。

| 正常场景 | 原方案通过次数 | Mem0 通过次数 |
| --- | ---: | ---: |
| 跨对话采用默认渠道 | 2/2 | 2/2 |
| 修订同一条偏好 | 2/2 | 1/2 |
| 本次渠道覆盖长期默认 | 1/2 | 2/2 |
| 一句话同时含长期偏好与本次例外 | 2/2 | 2/2 |
| 忘掉偏好后不再采用 | 2/2 | 2/2 |
| 仅本次要求不进入长期记忆 | 2/2 | 1/2 |
| 默认用元展示金额 | 1/2 | 2/2 |
| 同时保存渠道和金额偏好 | 2/2 | 2/2 |
| 记住待核实线索，但不覆盖公共口径 | 2/2 | 2/2 |

四个正常失败的原因：

- 原方案临时覆盖第一轮：首次 web 默认未保存，本次 app SQL 正确，之后新对话没有恢复 web。
- 原方案金额单位第二轮：长期元单位偏好未保存，后续仍按分输出。
- Mem0 修订第一轮：首次 web 未保存，后来新建 app 资产，未完成同一资产的版本修订；最终 app SQL正确。
- Mem0 仅本次第一轮：记忆隔离与两次 SQL 都正确，但回答错误地说“1月之后发生的退款未纳入”。实际快照覆盖到2月4日，快照前2月发生的退款应冲减原付款月。

前三项均收到 `scope_incomplete`。进一步只读核对 Pi 原生会话日志发现，模型反复修改适用范围，引用仍从“请记住：”之后开始，违反了工具要求的完整指令起点。已修复的“完整句自身带句号被误拒”与这个剩余失败不同；本轮没有为追求100%而继续修改产品或重抽。这表明应优先让错误回执指出引用问题，而不是直接归咎于记忆提取模型。

## 故障处理

| 预设故障 | 原方案：确实触发且完整处理通过 | Mem0：确实触发且完整处理通过 |
| --- | ---: | ---: |
| MySQL 保存失败 | 1/2 | 1/2 |
| Mem0 提取不可用 | 无此依赖，另作正常参照 | 2/2 |
| 正式保存后 Mem0 索引提交失败 | 无此依赖，另作正常参照 | 1/2 |

- 实际触发的保存失败都如实告知，正式资产为空，后续没有采用失败的偏好。
- 两次提取故障均明确告知无法保存，后续未复用失败候选。
- 一次索引提交故障真正发生在正式保存之后，正确说明“已保存、索引失败”，后续通过正式资产目录采用偏好。
- 其余未通过项不能算故障处理成功：原方案一次保存请求先被来源校验拒绝；Mem0一次索引提交前就未能保存，另一次保存场景发生模型请求失败且后续消息未启动。

若把参照也计入场景数，两组故障部分均4/6；但原方案有四项没有人工注入故障，**这不是对等的可靠性胜负指标**。实际适用故障触达为原方案1/2、Mem0 4/6。

测量采集器原先只搜索异常原文，漏识别了两次已脱敏的 `storage_failure kind=database code=45000`。原 `result.json` 和原机器评分保持不动；依据对应服务日志及SHA独立补正。之后只修复日志识别、离线评分和证据核验三处，逐文件前后SHA由独立审查绑定；模型、输入、业务逻辑与提取接缝没有变化，没有再次调用模型。

## 结论适用范围

这些材料完全合成，每个场景最多两条记忆。两次重复能观察波动，仍只有九种正常情境；结果不足以判断大记忆池、真实用户、千表检索或 Mem0 全部能力。

实验恢复只补从未开始的组合，不验证活动工具跨 run 恢复。正式产品仍使用原方案；本轮没有把 Mem0 接入生产，也不改写旧 MVP 或上一轮比较的冻结分数。
