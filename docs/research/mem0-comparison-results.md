# Mem0个人记忆检索对比结果

日期：2026-10-05。运行：`20261005T090450Z_17d3a6d5`。

## 建议

**本报告只测检索召回。此前据此给出的接入建议已撤回，当前接入判断见[完整 Agent 正确率对比](mem0-agent-comparison-results.md)。**

向量检索解决了部分中文换一种说法后找不到记忆的问题。Mem0与普通向量检索在这批问题上的召回和有效前5排序相同，增加了依赖、索引写入和历史存储。本轮未比较它的自动整理记忆能力，结论只用于判断已整理记忆的检索表现。后续完整 Agent 测量已另外验证真实整理与最终采用。

## 怎么比较的

- 使用实现之前写定的合成材料：24个逻辑资产、25个版本、32个中文查询，其中22个正例、10个负例。语料、答案和参数保持冻结。
- 三组各跑3轮，共288次正式检索，全部完成，失败0次。每组另有4次预热；重复用于测延迟和稳定性。
- 当前词法组直接调用产品中的Rust `retrieval::asset_directory`。
- 普通向量组和Mem0组使用百炼北京地域 `qwen3.7-text-embedding`，1024维、相同文本、无额外前缀或指令、相同L2归一化，使用同一Milvus实例的独立集合。
- Mem0 OSS `2.2.1`，`infer=False`；实际调用其写入、搜索与混合排序。关闭遥测、生成模型和重排。PyMilvus `2.5.18`实际连接Milvus `3.0.2`。
- 两组向宿主返回最多20个候选，回源核对用户、空间、版本、状态和知识依赖后保留前5个。Mem0内部沿用原算法的80条过取池，内部回执也接受身份检查。

## 核心结果

| 指标 | 当前词法检索 | 普通向量检索 | Mem0 |
| --- | ---: | ---: | ---: |
| 正例平均Recall@5 | 77.3% | 100% | 100% |
| 正例MRR@5 | 0.475 | 0.977 | 0.977 |
| 负例仍有候选的比例 | 100% | 100% | 100% |
| 查询中位耗时 | 3.1 ms | 131.9 ms | 142.6 ms |
| 查询p95耗时 | 6.7 ms | 305.7 ms | 310.6 ms |
| 边界违规 | 0 | 0 | 0 |
| 回源后元数据缺失 | 0 | 0 | 0 |

Recall@5表示每题所需记忆中有多少进入有效前5条，再按题平均。组合题需要两条记忆，找到一条计50%。MRR@5表示第一条相关记忆的位置，越接近1越靠前。

**这里的100%仅表示这22个合成正例找到了全部参考记忆。** 三组在10个负例上都返回了无关候选；本轮关闭可选阈值，以固定候选数量比较，不能把候选噪声当作Agent已经错误采用。此次检索指标不改写原MVP的12/16（75%）内容质量基线。

普通向量与Mem0的96对有效前5条排序完全相同。三个组内部，同一题的3轮有效前5排序也都一致；两向量组完整原始前20排序只有82/96对相同。按题比较，向量相对当前词法的召回有6题改善、16题持平；首条相关记忆的排名有1题退步。

## Mem0额外能力实际用了多少

- Milvus BM25关键词索引真实启用；96次正式关键词搜索全部可用，其中6次返回结果，9个输出候选获得关键词加分，最终有效前5排序保持相同。
- 可选spaCy没有安装。Mem0的英文词形还原与实体提取按库默认路径降级；实体加分为0，实体集合没有创建。本轮结果不能评价完整实体增强或中文分词优化后的效果。
- Mem0在索引中保留旧版本、停用或删除的旧记录。它们被宿主回源检查拦住：每个向量组分别拒绝旧资产版本、停用、删除、知识依赖改版各6次。这个效果来自应用的有效性检查。
- 最终上下文保留原始来源、范围、版本、私有归属及 `verified=false`。个人纠错没有成为公共口径。

## 费用、资源与维护

### 真实调用

共259次embedding API请求、12,120输入tokens：小样6次、建索引53次、预热8次、正式检索192次。全部收到有效回执，未知费用预留0，生成模型调用及尝试均为0。

按北京地域每千输入tokens ¥0.0005估算费用为 **¥0.00606**。这是API usage与公开标价的估算；未查询账户账单或免费额度。

普通向量组两份索引共4次批量embedding请求；Mem0的实际 `infer=False` 路径逐条调用，共49次。两组嵌入的总文本相同，索引输入token数都为2,744。两份索引合计构建耗时约8.26秒与16.49秒；耗时包含集合创建、API与flush。

### 本地资源

- 正式建索引、预热和查询总用时约57.74秒；Python客户端CPU约2.03秒，峰值RSS约149 MiB。它们是同一客户端过程的共享测量。
- 独立Python环境约299 MiB，包含46个安装包；包括Mem0、PyMilvus、OpenAI、Qdrant客户端、PostHog、SQLAlchemy等。遥测、Qdrant服务和生成模型没有启用。两组共用该环境，未单独测量Mem0依赖的增量磁盘量。
- Rust基线独立构建产物约1.62 GiB；本地运行目录当时约1.92 GiB，主要是依赖与构建产物。
- 本次创建6个独立集合，保留3个SQLite历史库，共84 KiB；3个预登记实体集合未创建。资源清单记录实际存在状态，已有产品集合保持原样。
- 托管模型加载时间、服务端CPU/RSS、各集合实际磁盘用量及Rust子进程CPU未测量。

## 可比性与结论范围

在线服务没有公开权重、分词器和池化的版本快照。重复文本的向量哈希会变化，因此只能确认两组使用同一模型名称、接口配置和客户端前处理，不能声称向量逐位一致。

只读本次集合核对两组存储的49对正文向量：最小余弦相似度为0.999998901，最大坐标差约0.000251。1,919对共有候选的最大语义分数差约0.000388；本轮有效前5排序全部稳定一致。没有为这项核对追加embedding请求。

当前样本小、记忆已人工整理。未比较自动提取纠错、长期冲突处理、完整Agent采用行为、Pi跨对话业务流程、真实MySQL权限事务、千表规模或真实业务试用。后续若继续评估Mem0，值得验证的是自动整理纠错的质量与成本。本轮没有实施这些扩展，也没有修改MVP产品源码、接口、根依赖或验收材料。
