# 原方案与接入 Mem0 后的 Agent 正确率对比

> 这是保存后再交 Mem0 整理的历史实验。用户质疑后已改为原始消息预提取并重新测量，见[修复后的比较](mem0-extraction-comparison-results.md)。本报告的原始数据与历史判分保持。


日期：2026-10-05。正式批次：`20261005T111708793Z_5ccd2fe6`。

## 结论

**这轮小样中，原方案完整场景正确率为 7/11（63.6%），接入 Mem0 后为 4/11（36.4%）。目前没有证据支持用 Mem0 提高本项目的 Agent 正确率。**

两组均使用真实 Pi SDK、DeepSeek Flash 和原有 Rust 业务链路。Mem0 组实际完成了记忆整理和检索。最终评分同时要求保存、跨对话采用、SQL 和解释正确；场景中有实质错误或运行未完成，整题计失败。

建议当前保留 MVP 的记忆方案。后续改进首先处理已发现的记忆保存校验问题，再判断增加记忆系统是否有收益。本轮没有修复产品或追加测量。

样本只有 11 个场景，各跑一次，且多个失败发生在 Mem0 接手之前。因此，以上数字是本轮接入配置的实测结果，不能推断 Mem0 本身导致正确率下降，也不能作为生产环境准确率。此前根据检索小样作出的接入建议已经撤回；旧召回率仅作为辅助证据。

## 比较的具体方案

| 部分 | A：原方案 | B：加入 Mem0 |
| --- | --- | --- |
| Agent 与生成模型 | Pi SDK、DeepSeek Flash、原生 high | 相同 |
| 正式记忆来源 | Rust 校验并保存到 MySQL | 相同 |
| 记忆组织与检索 | 现有个人资产目录、启动上下文和知识工具 | 增加 Mem0 OSS 2.2.1，真实 `infer=True` 整理和检索 |
| 向量模型 | 沿用原方案 | 百炼 `qwen3.7-text-embedding`，1024 维 |
| Agent 采用的正文 | MySQL 中的正式资产 | Mem0 找到候选后回源读取正式资产 |
| 版本、停用、用户隔离和 SQL 确认 | 原 Rust 规则 | 相同 |

Mem0 仅整理已经成功保存的个人资产及其来源。此次没有让它直接从任意原始聊天中创建正式记忆；它的派生摘要用于查找候选，正文仍回源。这是本轮实际验证的接入方式。

输入、答案和方案分别见 [固定输入](../../experiments/mem0-comparison/agent-inputs.json)、[独立要求](../../experiments/mem0-comparison/agent-expected.json)和[对比方案](../../experiments/mem0-comparison/agent-comparison-plan.md)。答案只在评分时读取，不进入模型输入。场景均为合成材料，使用独立数据库；新对话不携带学习对话历史。A/B 顺序交替，不重抽失败、不修改提示或题目。

## 结果

| 指标 | A：原方案 | B：加入 Mem0 |
| --- | ---: | ---: |
| 完整场景正确 | **7/11，63.6%** | **4/11，36.4%** |
| SQL 独立核算正确 | 10/14，71.4% | 9/14，64.3% |
| 已生成的 SQL 探针 | 12/14 | 13/14 |
| 完整输出的用户消息 | 22/25 | 24/25 |
| 运行未完成的消息 | 2 | 1 |

完整场景相差 −27.3 个百分点。按相同场景成对比较，B 有 2 题改善、5 题退步、4 题持平，其中两组均正确和均失败各 2 题。运行失败仍计入固定分母。

SQL 共固定 14 个探针，缺失计失败。实际生成的 SQL 都通过既有只读检查并停在用户确认前；正确率按独立 SQLite 种子及 5 个数据变体核算，同时核对任务渠道和单位。SQL 正确不代表解释、记忆保存或整个场景正确。

| --- | --- | --- | --- |
| 跨对话采用默认 web | 失败 | 失败 | 两组最初均未保存成功，下一对话缺少 web 条件 |
| 将默认 web 改为 app | 通过 | 失败 | B 最初的 web 未保存，后续新建 app 资产，没有完成原偏好的修订 |

| 一条消息中区分长期 web 与本次全部渠道 | 通过 | 失败 | B 首轮正确，下一对话模型回执未确认，没有完整 SQL 输出 |
| 停用默认偏好 | 通过 | 失败 | B 停用、检索和 SQL 均正确，最终解释却错误声称 2 月 1–3 日事件未纳入快照 |

| 正式保存后 Mem0 整理故障 | 失败 | 失败 | 两组均未成功正式保存；A 运行未完成，B 没有到达预设的整理故障 |
| 正式记忆存储故障 | 失败 | 通过 | 两组均实际触发数据库故障并如实告知；A 的下一轮模型请求未完成，B 后续全渠道 SQL 正确 |

### 机器评分与最终评分

机器评分为 A 6/11、B 5/11，独立内容复核作出两项纠正，原机器回执保留：

- `temporary_override::original`：默认偏好正文说明“仅当用户当次明确要求 app、store 或全渠道时，当次以明确要求为准，本默认不在该次生效。”机器把这段临时例外说明中的 `app` 当成长期 app 偏好。实际资产 ID、版本和正文均未变化，临时 app 和后续 web 的 SQL 与解释正确，最终判通过。
- `disable::mem0`：SQL 和停用流程通过，但解释有实质错误。固定业务说明与独立 SQLite 数据证实相关事件已纳入快照，最终判失败。

题目、产品要求和评分程序在正式测量中保持原样。上述差异是按既定要求修正机器判分，记录在独立审查中。

## 真正影响结果的问题

### 1. 纠错先在原有保存入口被拒绝

两组都多次遇到 `scope_incomplete`。已从实际 Pi 工具调用核实，[memory_source()](../../crates/data-agent/src/modules/assets/mod.rs) 对原话引用的边界校验过于严格：

- 用户说“请记住：以后我的分析默认只看 web 渠道”，模型只引用冒号后的偏好，会被拒绝。
- 模型引用了完整首句且保留句号，后面还有“现在不查数据”等第二句时，校验仍可能拒绝，因为它只检查引用后的字符，未认可引用自身已经以句号结束。

部分场景改为引用整条消息才保存成功。这个问题发生在 Mem0 整理之前，给它增加检索能力无法补救尚未写入的记忆。模型多次调整后仍遭拒绝，也增加了调用次数。本轮保留失败并记录原因，没有修改产品或重跑。

### 2. Mem0 已真实工作，但有效暴露范围较小

B 组完成 6 次真实整理请求，来自 5 个场景；一次停用删除了关联派生记录。正式记忆池至多两条，尚未测大记忆池或启动目录裁剪。成功提取不等于提高场景正确率：例如修订场景后续 app 已能正确采用，但第一次 web 保存失败仍使整题失败。

混合意图场景的 Mem0 派生文本还包含“本次 1 月全部渠道查询”等临时信息。宿主回源提供正式资产正文，限制了这类派生内容直接成为 Agent 的长期依据。这个观察说明自动整理仍需范围与来源校验；本轮没有测量直接采用派生摘要的方案。

### 3. 调用失败和解释错误分别保留

3 个模型调用没有完整回执：A 的 `index_failure`、`save_failure`，B 的 `mixed_intent`。它们按端到端不可用计失败，不归因为模型生成了错误内容；未知费用预留也没有释放。原进程中断的外层原因缺少完整日志，无法进一步断言。

`index_failure` 中，B 从未成功写入正式记忆，没有触发 `extraction_unavailable`，所以此次没有证明 Mem0 整理失败后的降级能力。`save_failure` 则在两组均通过服务日志核实了数据库 `SQLSTATE 45000`，不能仅凭场景名称宣称故障覆盖。
