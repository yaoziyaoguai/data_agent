## 1. 结论

**现有方向成立，功能范围已比较完整。现在最缺的是把已有设计变成明确的接口、可执行规则和验收证据。建议采用模块化 Rust 主应用，加独立 Worker；暂不将八个业务模块分别部署为微服务。**

已有资料足以开始有范围的接入试验，但尚不足以直接铺开全部生产实现。下一步先补四份小约定，再做一条从提问到结果、纠错和复用的完整流程。模型与检索参数在这条流程里验证，不要求所有细节先一次定完。

本轮回读了 [当前记录](CURRENT.md)、[上次 Oracle 审计](mvp-audit-20260928.md)、[语义理解与检索设计](semantic-retrieval-design.md) 及 C4 图源，并核对下列公开官方资料。没有重跑 Oracle，没有调用业务模型、连接数据平台适配器或执行业务 SQL。文档中已有“权限、版本、重试、结果完整性、纠错”的设计，不能再算作本轮才发现的新功能缺口。

## 3. MVP 还需补实的八项

### A. 让语义规则真正约束计算

**性质：旧审计已提出，尚未具体化。**

维护页已有算法、粒度、时间、过滤和关联，但尚无可执行的“本次计算条件”结构。例如月支付客户数至少明确：统计客户、客户键、整月支付时间与 UTC 边界、支付条件、非测试过滤、NULL 客户规则和引用定义版本。

建议首版：已维护的标准指标优先由确定的表达式或模板加参数生成；自由分析和复杂 SQL 由模型生成，再检查当前能够验证的对象、权限与计算约束。关键规则缺失时澄清。任意复杂 SQL 的业务正确性不能单靠解析器证明，仍需参考结果与反例验证。此处不要求先造完整语义编译引擎。

**完成证据：**修改正式计算规则后，计划、SQL 和解释一致改变；“每日去重客户数相加”等已知错误被检出。相关既有设计见上次审计第 1、7 项。

### B. 把 20 道场景变成真正的验收题

**性质：已有测试设计，尚未执行。**

现有题目说明了应找哪些依据、避免什么错；原审计时指标尚无经确认参考结果；公开版现以独立零售 fixture 准备验收，Agent 效果仍待运行。建议先从现有题中选 5 个代表场景作为起步样本：解释字段、单表月支付客户数、跨表分析、追问改维度、缺口径时澄清；随后跑完整 20 题及记忆/Skill 场景。这是推进顺序，不是把产品缩成只支持 5 个问题。

每题补：认可的条件、所需资料、参考 SQL、同一数据范围的参考结果，或正确的澄清/拒绝行为。保留未放进案例库的新问法。数据可能变化时，以同一版本、稳定测试数据或可比执行窗口核对，不能直接拿不同时间的数值判错。

**完成证据：**分别报告依据是否找全、口径/数值是否正确、错误拒答、耗时与成本；加入相似表和不同业务域，不能拿单张宽表成功代表全空间效果。无需新建评测平台。

### C. 核实数据平台适配器的实际接入约定

**性质：旧审计已识别，平台能力待核实。**

需要拿到代表请求/响应：元数据稳定 ID、分页与增量；用户身份和授权；执行方言及变量；预检；提交和平台查询 ID；状态、取消、结果类型、分页/截断；数据到齐信息能否取得。

尤其要明确“提交成功但回执丢失”能否按请求号查证或安全重试。查询取消需要真实平台终态；查询完成后解释失败，只重试解释。未知接口不代表数据平台适配器没有这些能力，接口暂未拿到也不自动把 MVP 改成只输出 SQL。

**完成证据：**一次真实提交、跟踪、读取和取消的联调记录；回执丢失、缺页等用可控故障验证。模型部署端点及哪些接入资料允许进入模型，也要在真实调用前明确。

### D. 明确 Rust、Pi 与 Worker 的运行状态归属

**性质：新增 Pi 后进一步暴露的接口缝隙；部分原则已有。**

Pi 的工具循环、Rust 的业务任务、Worker 的查询跟踪必须关联同一个用户、会话和运行。建议 Rust/MySQL 持有业务运行的正式状态，Pi 上报运行事件并保存可恢复条目；API 与 Worker 按同一套状态规则更新。

最少定义：运行 ID、工具调用 ID、平台查询 ID；同会话并发如何排队；任务谁领取、何时可接管；重复和晚到事件怎么处理；保存时机；模型/查询/解释各自完成与取消的状态。浏览器断开后应能回读任务，不因重连自动重新提交 SQL。

**完成证据：**Pi 或 Worker 重启、重复点击、流式连接断开、工具回执丢失，仍能正确显示和恢复；不同层的重试不能层层放大。现阶段可从 MySQL 持久任务开始验证，不预设消息队列。

### E. 修正或停用的记忆，不能从旧会话恢复回来继续生效

**性质：本轮明确补充的设计问题，没有声称现有实现已发生漏洞。**

已有设计会在检索后核对状态和版本，但旧记忆可能已经进入 Pi 的历史工具结果或压缩摘要。只删除向量索引，不能保证后续不再采用旧说法。

建议在新一轮或恢复时，核对带来源的知识、记忆、Skill 及当前权限；失效内容和依赖它的摘要需要排除或重建。更正后的规则必须作用于后续计算条件。对产品明确区分：停用记忆会停止自动复用；删除整段聊天及其保留期限是另一项操作约定。不能含糊承诺一次删除会抹去全部历史记录。

**完成证据：**先使用错误记忆，再压缩/重启，再更正、停用或撤权，换个问法仍遵守新状态。跨用户隔离与绕过工具检查的 Skill 也要作为首版反例。

### F. 把用户提问的整条交互做完整

**性质：原八模块待细化，并非维护页需要推倒重来。**

已验证的是维护页和模拟个人空间。提问主页尚未把“澄清 → 本次条件 → SQL → 执行 → 结果 → 纠错 → 保存并复用 Skill”连接起来。

首版应明确：只要 SQL 与要求取数的区别；追问如何保留条件；修改条件后如何重算；执行中/取消中/状态未知；结果已取得但解释失败；空结果、零值、未取全、数据未到齐的区别；采用了哪些定义和案例。详细内容可以展开，不能把后台日志全塞给用户。

**完成证据：**一条最薄的真实流程能完成提问、追问、纠错和一次 Skill 复用。无需先把全部页面重新设计一遍。

### G. 全空间预填不能堵住用户正在进行的分析

**性质：旧预算原则尚未落地；全空间同步使它成为实际问题。**

初始预填、上游追溯、索引更新、个人记忆处理和在线分析都会消耗模型或后台资源。建议区分在线与批量任务的并发配额、优先级和调用预算；源版本没变时复用已有解析/分析，避免无差别反复预填。

一个运行需要串起采用的知识版本、模型与工具调用、平台查询、失败阶段、耗时和成本。维护者需要可查看的失败/待复核任务与重试入口，可以作为现有页面的小列表。

**完成证据：**批量预填进行时，在线请求仍能响应；失败可定位，可停止、重试且不覆盖人工修改。实际限额依据样本确定。真实试用前再完成最小的配置、健康检查、数据库迁移、备份与恢复约定；无需另建运维平台。

### H. 候选组件先证明能减少工作量

**性质：选型尚未验证，不是缺产品模块。**

Pi 已由用户确定，需验证实际接入；Mem0 仍为候选。DeepSeek 的生成接口不等于已解决文本向量化。建议先验证 DeepSeek 实际端点的工具调用、Pi 工具白名单与会话恢复、中文术语/英文标识的检索、纠错替代与删除。

Mem0 默认自托管套件不是已验证的 MySQL/Zilliz 组合。个人记录、明确纠错与显式 Skill 复用可先基于应用正式记录完成，记忆提取/检索引擎通过已有边界接入。用户资产能力属于基础，某个开源引擎不是硬前置。官方存在适配器不等于我们已经联调成功。

## 4. 实现前到底还要定什么

### 先写清四份小约定，再开始第一条流程

这些约定应放在现有设计中，不需要各自新建一套文档。

| 约定 | 最小产物 | 解决的问题 |
| --- | --- | --- |
| 平台接入 | 数据平台适配器身份/查询/结果/资料的代表请求与响应；模型和数据访问边界 | 能接什么、失败和未知状态怎么表示 |
| 计算与知识对象 | 一个实际的计算条件示例；对象/版本/引用、编辑冲突与生效规则；最小 MySQL 和索引字段 | 同一个问题到底怎么算，哪些内容是正式依据 |
| 运行与工具 | 会话、运行、工具、平台查询的关联；任务领取、恢复、取消、重试责任；最薄接口 | 进程中断和多用户并发时由谁负责 |
| 业务验收 | 首批代表问题、认可条件与参考结果、错误反例、主要页面状态 | 什么叫这版能用，改动后如何判断退步 |

平台具体信息由现有接口和联调证据提供；业务参考答案需要数据开发或相关业务资料确认。其余结构和方案由实现方先给具体草案，不把陌生技术选择全部交回用户。

### 在第一条完整流程里验证

建议用“计算上个月支付客户数”：同步并引用资料 → 语义规则 → 检索 → 计算条件 → SQL 检查 → 平台执行 → 结果和依据 → 追问 → 纠错 → 显式 Skill 复用。先用模拟工具验证状态与接口，再在明确的数据访问范围内联调真实平台和模型。

在此过程中确定 Embedding 候选、已选 Pi 的具体接入、SQL 方言支持、索引参数、耗时与预算；逐步补最小表结构和 Rust 接口。参考答案、基本契约应先于其对应实现；完整数据库设计、所有模型参数和全空间效果不应成为任何编码开始前的无限前置条件。

## 5. 微服务：现在推荐怎样做

**推荐一个模块清晰的 Rust 主应用，API 与 Worker 分进程运行；已选 Pi 推荐通过小型 Node.js 组件嵌入 SDK。**

| 运行单位 | 职责与边界 |
| --- | --- |
| React 前端 | 提问、结果、语义维护、记录、记忆与 Skill |
| Rust API | 身份与权限、正式业务记录、计算条件、语义检索、受控数据工具与任务接口；内部按职责分模块 |
| Rust Worker | 同步、预填、索引和查询跟踪；共用业务代码与 MySQL，可按任务角色限制资源和增加实例 |
| Pi（已定）/ Node.js SDK（接入建议） | 模型自主调用工具的运行循环、事件和会话；数据工具经 Rust 校验。可与主应用一起发布 |
| Mem0（候选） | 需要时接入候选记忆提取与检索；不默认部署其完整套件 |
| MySQL、Zilliz/Milvus | 正式记录、派生索引；业务明细及查询计算继续由数据平台适配器/数仓负责 |

C4 中的容器表示运行组件或存储，不等同于业务微服务、Docker 或部署机器。API/Worker 分进程可以隔离长任务、分别扩容；语言运行时不同也可以有单独进程。

现在全面拆微服务的主要代价：

1. 指标、检索、SQL、纠错和 Skill 的规则仍在共同变化，容易变成一次需求协调多个接口和发布。
2. 一次查询会产生更多跨进程调用，需要额外处理网络失败、兼容、超时和追踪。
3. 正式语义/纠错与索引任务原本可在 MySQL 同一事务保存；拆成独立数据所有者后，要额外解决跨服务一致性。
4. 表选错、关联放大、旧记忆、重复提交等当前主要风险仍需业务规则与验证，拆服务本身无法解决。

依据包括 [Microsoft 微服务架构指南](https://learn.microsoft.com/en-us/azure/architecture/guide/architecture-styles/microservices)、[Web-Queue-Worker](https://learn.microsoft.com/en-us/azure/architecture/guide/architecture-styles/web-queue-worker) 和 Fowler 的 [Monolith First](https://martinfowler.com/bliki/MonolithFirst.html)、[Microservice Premium](https://martinfowler.com/bliki/MicroservicePremium.html)。微软的 Worker 示例采用消息队列，不能据此声称其推荐 MySQL 队列；MySQL 持久任务是本项目需要验证的简化方案。Fowler 的文章是架构经验，非当前行业统计。

**出现以下实际证据，再按稳定边界拆一块：**需要独立发布且共同发布经常阻塞；有独立维护责任和运维能力；负载证明现有 Worker 角色扩容不足；需更强故障隔离；存在明确的独立部署或数据访问要求。拆分前须明确接口和数据所有权。上千张表的目标目录、引入 Node.js/Python 库、图上出现多个框，均不单独构成全面微服务的理由。

## 6. 哪些仍可后做

| A05 / P1 | M03仅去重未防回退；两个有效同步作业，S2先提交、S1后到，旧头可能成为当前来源 | 采集起点版本CAS；迟到快照留历史但不推进头，冲突必须重新采集/查证；M03 | 两作业租约均有效时，迟到S1仍不能替换S2或让旧预填生效 |
| A06 / P2 | M04只取首批候选，过滤历史版本或无效项后没有补取；后续有效资料被漏掉 | 回源过滤后按类型有界补取，配额满足/候选耗尽/工作量上限三种结束；M04组合用例 | 首批全失效或旧版本占满时仍找到后续有效对象；达到上限说明覆盖不完整，不泄漏权限过滤计数 |
| A07 / P2 | POST knowledge及首次目录同步没有无base_version的创建操作；新表没有对象也没有依赖可查 | 补首版创建、稳定来源键和幂等；同步区分创建新对象与标记既有依赖；M02/M03 | 空目录导入后对象、引用、首版和索引待办齐全；重复/并发导入只建一个对象 |
| A08 / P2 | propose_semantic_change有工具名，没有提案记录与正式保存闭环；可能被临时接成直接改公共定义 | 提案与正式版本分存；本人读取，维护者明确保存另核权限/基版本/公共资料范围；M02 | 生成建议不改当前版本；过期建议冲突；私人来源不隐式变公共；同操作应用不重复 |
| A09 / P2 | V02声称AppTx不提供越界写表权限，但单库SQLx事务与pub(crate)不能保证这一点 | 明确Rust隐私、工程检查和数据库授权各自保证；限制SQL位置与表owner；AGENTS/V02 | 协调层裸SQL、兄弟模块互导反例必须被检查拒绝；不把普通编译通过当作表级隔离 |
| A10 / P2 | 组合层要求预锁运行/任务/查询，但只有会话有明确锁接口，容易逼出裸SQL和倒序锁 | 所属模块公开少量lock操作，返回当前事务有效快照，普通read不暗含写锁；M05–M08 | 确认、提交、取消、结束按同一锁序；协调层不写FOR UPDATE；死锁重试不重复外部副作用 |

### 9.3 防止代码长成巨石的实际约束

- M08只保存运行、工具账本、检查点、输出和预算规则，内部按职责分开；不吸收选表、条件修订或查询提交。
- 用例负责组合事务，模块负责自己的判断与SQL；通过公开锁接口取得同事务事实，不在协调层再实现一遍状态机。
- HTTP、Pi工具和Worker复用同一用例；契约真源、边界解析和映射明确，避免入口各写一套规则。
- 私有存储、禁止模块互导、SQL位置/表owner约束要在I0落实检查，并用越界反例证明检查有效。文档声明与依赖图无环不足以证明未来代码遵守它们。
- 产品不变量、模块契约、组合映射各有明确来源；生成图册不手改。后续行为变更必须同步相关来源，避免再次出现取消范围漂移。

### 9.4 仍需实现证据的事项

1. **I0编译与协议小样：**固定契约生成/运行时解析工具，生成消息、工具调用、确认和错误的代表类型；用正反例验证Rust/Node/Web一致。实现最小迁移的唯一约束、事务和边界检查。
2. **Pi故障小样：**固定SDK在业务提交前、提交后但Node未收到回执、最终输出后检查点未提交三个故障点恢复；新run接回原operation；失效资料及依赖它的摘要/回答不再次进入模型。无法证明恢复清单完整时按允许事实重建。设计不能证明SDK已支持。
3. **对应增量并发验收：**A01–A10列出的反例进入各模块实现验收；尤其消息/确认竞争、撤回连续游标、同步来源防回退和首次导入。不要用静态文本匹配冒充这些行为测试。
4. **真实模型与检索：**先确定端点、模型及费用上限，再用合成资料取得DeepSeek工具调用证据；Embedding、补取上限和千表效果由试验固定。数据库/向量库已能连接，不等于这些能力完成。

这些项按I0/I1/I2逐步取得，不要求先建设整套新基础设施。本轮没有需要用户重新选择架构的新增产品取舍；真实模型配置与费用上限仍须在实际调用前明确。

### 9.5 本轮验证范围

审计采用具体反例走查接口、状态和事务；图册重建与文档检查另记录到 CURRENT 的“最近验证”。检查只覆盖设计材料、引用、同源生成和浏览器展示，不证明业务并发、权限、模型、平台或跨进程恢复通过。未启动数据库、未调用模型、未创建正式业务服务。
