# Pi 接入复用与既有实现修复

日期：2026-10-29。本文是06–09的共同实施约束，覆盖01–05已落地的接入代码，不是仅约束将来的新增代码。当前阶段和证据仍只看 [CURRENT](../../CURRENT.md)。05尚未关闭时可以审查本包，不能据此修改05冻结输入、启动06或关闭05。

本包细化 [实现设计](../../architecture/implementation-design.md) 第17.4、17.5、17.7、17.8节，不改变业务合同、模块拓扑或模型限额。锁定依据为根package.json/package-lock.json和已安装的三个 `@earendil-works/pi-*` **1.3.0** 包；接手时核对实际版本。发现不同版本先核实对应API，不套用旧结论，不因本文顺手升级SDK。

## 3. 06先修接入，再扩工具合同

### 检查点：受信运行内只导出原生引用

1. 复用既有长期会话合成夹具，用相同尾部和相同工具次数对照较短/较长历史，统计本次导出实际文件读取/JSON解码次数与字节，记录总耗时但不设置依赖机器速度的固定毫秒断言。只在测试进程收集，不加生产遥测或持久计数。
2. 完整检查保留在**外部导入、进程恢复打开**的读取边界，原生新建状态由SessionManager初始化。导入的内联内容和目标已存文件是不同输入，相容性仍需核对；同次打开不反复做宿主严格整读。已由本运行持有的SessionManager导出时使用其session/file/leaf引用与现有持久化路径，不每个工具重读全历史。允许首次严格读取后Pi再加载一次；不为消除这一次读取使用SDK私有字段或重写加载器。
3. Pi读取器对坏行的宽松处理不能直接代替当前严格恢复合同。保留缺文件、坏JSON/UTF-8、重复/无父条目、错误session/leaf、路径越界及已有符号链接负控；拒绝时不能修补、覆盖或创建新会话冒充成功。正常运行内未变历史不再受这些检查重复扫描。
4. 保留现有必要文件持久化和确认顺序：Pi条目落盘后，宿主才保存引用；原MySQL确认leaf控制恢复分支。崩溃后不能提交指向未持久条目的引用，晚尾分支不替代已确认leaf。不要借性能优化删除fsync或改变原成功/未知工具恢复语义。
   锁定SDK会先更新内存条目/leaf再调用写盘，`isPersisted()`只表示启用持久化；它与fsync成功均不证明当前leaf已写入。先在原生追加/首次flush及必要同步处注入失败，核对异常如何经过SDK到达宿主。追加或同步失败后，错误出口不得仅凭内存leaf发布新检查点、替换宿主确认引用；保留原确认事实并传播失败，需要导出时只在故障路径严格核验。原文件仍完整则原leaf可恢复，已经损坏则保持明确拒绝，不修补或换会话冒充成功。健康路径去掉整本扫描，不新增持久偏移、镜像、写盘监控或重放框架。错误路径未被小样证明前，不能删除现有保护。这是已有持久化合同的实现要求，故障发生率未知。
5. 不增加会话文件监听、历史哈希链、日志缓存服务、数据库镜像或永久偏移表。若实现遇到原正常路径的新问题，先给最小反例；极低概率外部改文件/跨机争写等假设不得无依据扩展保护。发生率未知就写未知。

沿 `check-checkpoint-journal.mjs` 与 `check-pi-sdk.mjs` 补成本和恢复反例，兼容嵌入entries、host_checkpoint与pi_session三个既有入口；不是要求三者永久并行写入。持久存储格式、session/entry/tool ID保持，08只再做跨版本整体演练，不推迟本切片可运行的兼容修改。

### 传输：已校验值通过类型传递

1. 复用 `RustTransport` 的路径/响应合同映射和同源生成类型，把JSON解析和响应Schema校验留在实际接收边界，向调用者返回已校验类型；删除同一输入/回执在同侧无变更情况下的重复validate/decode。只改当前直接受影响调用点，不做全仓类型迁移或万能RPC框架。
2. 区分工具参数Schema与外层调用信封，它们不是同一检查；区分SDK参数处理、Node→Rust的跨进程边界及权限/版本等业务规则。只有相同数据、相同Schema、相同信任边界的重复才删除。Pi内部校验是否等价必须看锁定实现，不能仅凭有TypeScript类型便跳过外部输入校验。
3. 正常新调用走当前合同；恢复已登记旧调用继续先接原账本/回执，不在前面强加新参数Schema。不确定是否提交仍保持原错误，不能通过少校验让未知操作换ID再发。
4. 合成传输边界验证合法响应、错误形状、未登记坏参数、旧成功调用和拒绝回执；重复校验次数只作本次窄诊断，行为通过看实际不重复业务调用、错误仍明确以及回执内容一致。测试替身应实现调整后的边界合同，不为了旧替身未校验而把重复逻辑加回产品。

完成这两项及原SDK接入回归后，继续 [06详细规格](evidence-delivery.md) 的一条knowledge＋一条raw纵向小样。不要先铺完整v2字段。response_budget是宿主容量提示，Rust裁剪一次、Node无损包装，空间不足继续用Pi原生压缩；模型自行决定补读，不增加固定检索→全文→摘要的流水线。

## 4. 07答案只补业务归属

Pi会话保存完整消息，但不能替应用决定哪条是正式业务答案。沿 [07规格](task-answers.md) 复用真实SDK条目及已持久输出/成功答案回执；保留有序part引用，不另存可修改正文或新增答案账本。

- 普通单任务仍自然回答，不强制额外工具或模型调用；“我先查一下”的message_end不定稿。
- 多任务切换沿既有route的显式finalize_current_answer；查SessionManager中的所属完整消息并await现有output.drain，再由Rust同事务冻结引用和切任务。没有额外的模型汇总调用。
- 成功的present_analysis_answer回执是已核验内容来源；“已定稿”以Rust已提交、可恢复的part绑定为准。未提交绑定的候选仍按同任务失败规则失效；查询回执与part是否同事务提交须在本包合同中明确，不能仅凭Node缓存非空判断。旧v1回执缺part字段不自动成为新式定稿；普通route不定稿。
- await session.prompt/sendCustomMessage等原生命周期负责本轮结束；需要事件观察时用Pi语义，不能自行轮询isStreaming猜收尾。message_end可用于取得完整消息，不能单独证明宿主存储完成。
- `agent_before_settle`与最终提交共用交付选择：通知核验答案优先，其次当前核验答案，最后合法控制；`needsResultAnswer`未满足时不得先编辑为控制。`completed`只表示本活动成功，保SDK的continue/pendingMessages续接，canContinue不代表必须再调模型。用运行前原生entry身份集合定位本轮，压缩移出user也不回扫旧轮。通过原生context_edit提交草稿，确无本轮正文才追加宿主事实；恢复在extension前直接finish的快路也用appendContextEdit/宿主消息后导出checkpoint，不增加模型整理调用或持久轮次账本。
- 只保护**已经定稿**的任务部分；同任务未定稿答案被后续失败置无效的原规则继续。不能把所有历史助手文本拼起来修“最后一条”问题。
- 同步迁移旧单槽的最终选择、text_delta落库条件和查询答案来源要求。判断针对当前任务/当前消息，不能因A已有part就全局停止B正文写入。半轮恢复会直接走invokeRecorded且早于新outputStream创建；沿原工具登记保留宿主绑定的条目/原输出attempt与片段引用，先接原登记/回执，不使用新attempt的空范围、不等待旧message_end重发。分别验证登记后未冻结和冻结后丢回执；缺原片段仍明确失败，不新增正文副本或答案账本。
- 互斥来源的A正文不能进入B实际provider输入，包括摘要；最终展示可按任务确定性组合，组合文本不反向作为无范围正文注入下一轮。

## 5. 08和09验证，不补造SDK框架

08使用现有迁移、启动入口和Pi会话存储，演练旧checkpoint/工具回执/任务和新v2的组合；Pi JSONL格式与应用业务Schema分别处理。不新增通用迁移框架、长期双写索引或独立恢复服务，不把SDK升级当作前提。

09沿已有语音座舱用例验证长期会话、压缩、多任务及资料取证。小样/本地协议证明接线，真实模型证明该模型实际行为，二者分别报告。01–05已证修复在06–09有归属，不能以它们“之前已关闭”为由略过；也不因本包开展而把01–05全部重做。

## 6. 验收与成本控制

| 检查 | 必需证据 | 所属包 |
| --- | --- | --- |
| 长会话引用导出 | 历史规模扩大时，同一次健康已加载会话的导出不重复全量读/解析；内存leaf先推进而写盘失败时不发布无效引用；原session/leaf、压缩、原工具身份及损坏文件拒绝保持 | 06；08跨版本 |

| 原生生命周期 | SDK自动压缩与临时重试仍走原budget；取消、半轮工具接回、范围重投影保持；不另增模型循环 | 06/07 |
| 多任务定稿 | A完成、B中断恢复、刷新两答案；同任务未定稿失败、B正文仍落库、route登记未冻结/冻结丢回执分别恢复；实际B请求与摘要无A受限正文 | 07 |
| 工具交付 | 裁剪后的真实回执进入Pi/provider；支持内容而非ID、原游标和回执恢复一致 | 06/07 |
| 旧状态升级 | checkpoint/session/operation/budget不换，v1旧调用与v2新消息共存恢复，索引先切换 | 08 |
| 真实效果 | 已授权模型的分层语音座舱场景及未通过根因；没有授权则如实保留该层缺口 | 09 |

优先扩展已有 `check-checkpoint-journal`、`check-pi-sdk`、`check-request-policy`、`check-native-compaction`、`check-recovery-continuation`、`check-sdk-event-order`、`check-answer-state`、`check-tool-serialization` 及对应业务测试。新增检查必须命名为业务行为，不含包号/阶段号。无需全量检索索引来证明Node同侧校验或JSONL导出；普通失败先跑相关窄反例，稳定后按本增量正式验收一次。千表检索/完整重建保留在其覆盖的尺度或恢复验收，不因每次小改机械重跑。

数据库harness串行，原生SDK/协议检查与真实模型/存储分开；不构建测试缓存/断点续跑平台。整组时限按实际测试构成和耗时设定，不能把测试组上限当产品10秒期限或单消息模型限额。验收期间输入保持不变；失败先定位，不把旧passed拼成新收据。

每包独立审查追查“明确业务要求→Pi已有能力→最小适配→最终消费者→运行证据”，重点核三项既有问题确实修复，且保留表中必要适配。主实施者不伪造他人审查；没有失败证据的低概率保护先向用户给出触发、依据和代价，不编概率、不自行实现。
