## 两个问题如何定位与修复

**一、从相关资料找到可用于草稿的字段依据。** 从 `apps/agent/tools/data-tools.ts` 和 `apps/agent/session/resources.ts` 的**实际模型请求**查起，接着对照 Rust 的检索、精读与任务纳入回执。将每个需要的依据分别记为“发现了、内容交付了、带正确修订纳入原任务了、草稿实际引用了”；不能用数据库里有该对象证明这四件事。平台字段元数据与正式知识字段记录是两类身份，有正式定义时要能使用该条的 ID 和修订，无正式定义的字段不能编造一个知识身份。是否需要引用某个字段由题目和实际资料决定，不要求所有字段都有正式定义。

1. 先复核现成的说明与显式选择用例，再做一个**不替 Agent 选好答案**的对照：保留原任务约束，用普通检索入口查找晚于目录第一页的相关字段。受控模型可以证明查询、精读、纳入与 `request_query` 的具体通路，不能证明自主工具选择。没有必要把 198 项全部塞进模型，也不能把原题字段名、测试答案或必须按序调用的脚本写入产品。
2. 记录第一次出现差异的位置：相关对象未召回，优先看实际检索输入、范围及 owner 输出；召回或精读给了正式身份却未进入任务，查既有纳入工具与 Rust 操作回执；Rust 给出了正确内容但模型没有看见，查交付或上下文组装。只改确有证据的那个位置。如果当前候选在这些边界都正确，把“Flash 自主选择是否改善”留给有效授权下的原题，不增加提示、检索降级路径或新的 Agent 循环来猜原因。

**二、只交付用户限定的字段。** 用不含原题专名的合成对象：一个表含多个字段，限定其中三个，另放可辨识的未选字段。分别采集用户/任务已表达的限制、Pi 实际送出的工具参数、Rust 权威回执、实际发给模型的工具正文，以及随后任务的依据。仅记录必要字段标识和内容摘要。用户限定的业务证据范围与数据平台读取权限分开判断；有权读整表不代表本题要读整表。

| 首个出现偏差的位置 | 最小修复及反证 |
| --- | --- |
| 工具参数已经是整表，尽管现有输入能表达窄读 | 核对工具说明、模型可见的选择/范围以及后续是否沿用了该选择；先证实何处丢了限定。不要把合法的显式整表读取一律改为三字段。 |
| 工具收到三个字段，Rust 回执却含其他字段 | 沿 `crates/data-agent/src/use_cases/` 中现有 `data_tools`、`evidence_delivery`、`knowledge_sources` 或 `knowledge` 实际 owner 定位；在最早拥有已验证范围且能做投影的入口修一次。不要在 UI、Pi、Rust 三处各做一遍过滤。 |
| Rust 已经窄读，只有模型请求或恢复后的正文变宽 | 查现有回执映射和恢复时所引用的对象，修错误的映射或重读。不能只改界面显示；模型已看见多余字段仍算失败。 |
| 当前版本在上述边界均只含限定字段 | 保存证据，明确旧轨迹是否能还原首个偏差。不能据此追认旧题通过，也不为假设性路径加兜底。 |

可观察验收：三个允许字段各有来源，其他字段的**业务正文和定义**不出现在此限定读取的模型正文/可用任务依据中；同一对象明确允许整表的对照仍按原接口工作。仅有表 ID、修订、分页等定位元数据不等于读了字段定义。先跑能区分假设的 RED，再修、再 GREEN；已绿行为不制造假 RED。

## 原题和验收的不可变部分

- 以 `.local/audits/data-agent-flash-root-cause-20261117/source-original-pair.json` 的两条原始用户消息为准，按顺序送进**同一对话、同一业务任务**。从本包复制题意摘要、把两条合并、额外提问、手选缺失依据、放宽执行权限，都不能替代原题。将原消息文本逐条按 UTF-8 计算摘要核对；原判据来自冻结的验收资料，不能从候选输出生成。缺少本地受控资料时停止该部分并说明，不能自行重构原题。
- 第一轮检查完整的九月草稿：以 UTC 交互开始和合格轮次为基础，使用在固定截止点前可见的最大尝试序号；分母包含超时和取消，分子按成功定义；实际 SQL、条件、数据范围与原独立判据逐项核对。三张主表按原题；车辆资料只允许 `vehicle_id`、`is_lab_unit`、`telemetry_consent`。依原验收允许的映射区分平台字段与正式定义。只有引用、解释、重复询问，不算草稿。
- 第二轮只把统计月份改为八月；原截止点 `2026-10-04T00:00:00Z`、来源、限制与其他口径保持不变。须能从持久记录指回第一次草稿及同一任务，看到第二份对应月份的草稿。两轮平台执行数都必须是零。保存模型、平台、存储分别使用了什么，以及平台无执行的证据；不靠助手一句“没有执行”判断。

## 执行顺序与交付

1. **冻结现场。** 对比当前 HEAD/工作树、原题摘要、旧基线/绑定清单、报告及已有候选证据。先保留旧失败和已有改动。本包不授权清库、改原题、换模型、改费率/余额、调宽断言、提交推送或更新日常服务。
2. **免费定位。** 复用 `node tests/runtime/check-request-context.mjs`、`node tests/mvp/check-source-search-admission.mjs`、`node tests/mvp/check-source-search-admission.mjs source-selection` 的既有路径；数据库试验只用原隔离 harness，串行。旧精读如需回归，用现有 `tests/mvp/check-source-selection-cursors.mjs` 的已登记命令。先看 `Makefile` 和现有日志确认参数、构建产物与当前源一致；合成 provider 隔离真实模型凭据。保留工具形状与请求容量基线。只有新行为或未区分的边界才补一个最小测试。
3. **只修已经定位的 owner。** 保留 Pi 1.4 的唯一工具循环、会话恢复与原生压缩；Rust 继续掌管任务、权限、来源版本和草稿。不新增模型、通用策略层、并行解析器、特殊表规则、无提示的整表回退或付费测试自动开关。不以改旧报告、改冻结检查、臆造 ID、把精读变成无限扫描来消除失败。
4. **真实复验有单独门槛。** 历史 200 元授权已于 2026-11-18 17:27（北京时间）到期，不能将剩余余额继承给新跑。只有用户新授权，且核实当前的金额、期限、Flash/high、原隔离环境与两条消息后才发起。原每消息调用上限和连续失败停止规则不变，不换 Pro。无授权就交付免费部分，标为 `未运行：需新授权`；本包本身不是授权。一次原题对照仍失败则保留实测轨迹，停在首个能解释的差异，不连续花费碰运气。
5. **结果交接。** 分别给出两问题的因果链/尚不可判定之处、改动文件、RED/GREEN 或原已绿证据、原题与冻结绑定核对、两轮的草稿/执行/范围证据及授权状态。只有在对应验收实际完成后才更新 `docs/CURRENT.md` 的状态。沿现有流程依次做相称回归、`make verify-delivery`；若要关闭整个增量，须用原绑定完成 `make verify-increment` 和独立审查，状态与证据一致。不得把两个工程检查、静态通过、单项补跑或未执行的真实验证报成全局通过。
