## 4. 查询准备期间维护原领取

先以§6的隔离慢准备场景证明旧代码失败，再改产品。优先保留现有15秒查询租约，解决工作仍在进行却无人续租的问题，不能仅扩大TTL或去掉到期判断。

### 4.1 M07续租操作

在queries模块提供一个范围明确的续租操作，由私有store执行条件UPDATE。输入来自本次真实领取的query ID、owner、epoch；核对数据库中同owner、同epoch、原租约尚未过期和现有可处理状态，才推进原`lease_until`。返回原Result语义；无匹配行返回`lease_lost`，真实存储错误保留原分类。不得顺带改业务状态、授权、预算、尝试次数或终态。

续租使用原job的query ID、lease epoch，以及本次`process_due(pool, worker)`入参worker。这里的owner是`query_requests.lease_owner`；`job["owner_id"]`/`ctx.user_id`继续用于业务权限和平台用户身份，不能拿它匹配租约持有者。无需扩充领取payload或新增领取身份结构，不改HTTP/Pi合同。

领取、续租与事务交接刷新同源使用现有15秒值，心跳间隔按其三分之一推导，不增加配置页、环境参数或新的最大次数。内部实现沿现有业务命名，必要导出只通过queries公开入口，use_case不得直接写SQL。

### 4.2 组合范围与事务交接

复用`deliver_run::start_delivery`现有结构：一个future推进查询准备，一个future推进同领取续租，由`tokio::select!`同时轮询。准备范围覆盖领取后的读取、`check_text_results`及原锁内来源/版本核验，直到`begin_submission_in_tx`所在事务成功提交。心跳立即开始，准备成功/失败或确定失租时结束，不遗留后台task。

**不能写成外层select命中tick后，再串行await续租并暂停准备future。** 当准备持有查询行锁时，续租可能等待该锁；准备必须仍能继续提交。既有消息准备实现已展示这一约束，直接复用其结构，不抽通用框架。

保留`begin_submission_in_tx`原有领取有效性检查和动作判定。在提交事务末尾，以刷新语句所用数据库时间加同源15秒设置原查询到期时间。**执行刷新的UPDATE本身必须要求原query ID、epoch及租约仍未过期**；无匹配行返回`lease_lost`，沿现有事务错误路径回滚，不能仅依赖更早的SELECT核验。持有行锁不能阻止时间流逝；这里只重核会随时间变化的租约，不重跑来源预检或权限校验。

此次刷新不改变owner/epoch，不额外增加`submission_attempts`；原queued→submitting计数行为保持，失败事务不留下该次新增计数或可交付的平台动作。15秒从数据库刷新时刻计算，不能承诺commit回执返回后还严格剩余完整15秒。

准备组合保留并带出原`conv`、`packet`和`authorization_error`等必要结果；事务成功commit后，仍先沿原授权失败拦截，再进入事务外的平台动作。保持现有5秒单调用超时、submit/lookup/cancel及观测落库/原结果通知语义；5秒平台超时不等于后续观测事务也必在固定时间内完成。

本包只修已证的提交准备覆盖，不扩成无限续租平台调用、永不失租或一切网络故障必成功。原后续epoch重核和未知查证路径保留；不改平台幂等键或另起自动执行循环。心跳存储错误沿现有明确临时错误分类处理，最终提交仍须通过原有效租约检查；不把任意异常当作可忽略。

## 5. 修正这条验收的等待预算

`harness.capture`当前send后固定用20秒until。兼容增加一个可选等待毫秒参数，默认仍为20000；`check-conversational-query.mjs`的begin显式传120000，仍以同conversation ID和本次message ID精确匹配。参数只是测试观测期限，不影响产品超时、租约、重试或授权。

该测试最初“自动归属查询完成”也用默认20秒。按实测慢准备及启动成本，将此等待显式设120000；预期仍是原查询`succeeded`与单次平台提交，不能接受queued、进程存活或超时视为通过。其他场景不批量扩时；若遇新的等待失败，先区分真正业务错误与同一已证耗时，不直接套600秒或循环重跑。

在CURRENT的“验收与要求变更”写清原20秒、新120秒、来源于54.2秒消息到达及超过15秒准备的探针证据。原消息、SQL、结果、授权、重放与隔离断言全部保持。不得全局更改`until`默认值或把测试超时改成无限等待。

54.2秒是该探针从发起消息至收到run的总耗时，不是查询准备耗时；capture中的until在send返回后开始。不能用该数字反推历史宿主瓶颈、服务器SQL耗时或产品响应时限。

## 6. 有界证明与检查

### 6.1 新回归只证明一个缺口及其必要边界

1. 保存、明确确认一份合法合成查询，沿原测试控制入口完成消息并暂停Worker，不换授权身份。
2. 在仅属于测试的会话行上持锁，再启动Worker；从独立连接确认目标query已领取，记录原lease_owner、epoch与到期时间，再保持阻塞越过该领取的原到期时间，避免只证明领取前等待。
3. 观察相同owner/epoch的到期时间实际推进，期间实际平台submit请求0；释放锁后原查询成功、该query的实际平台submit请求恰好一次、原结果通知沿原消息预算。
4. 新用例等待期限明确容纳主动注入的阻塞；旧代码须因未续租而失败，不能仅断言最终成功，因为重新领取后成功会掩盖缺口。

同owner/epoch要求限定在准备阶段及首次提交承接；不要求最终succeeded时仍是最初epoch。现有`record_observation_in_tx`会将期限置为约250ms后，运行中的查询可通过后续正常lookup重新领取并增加epoch，不能误判为失败。

一次提交以实际`/submit`请求为依据，不能仅看`submission_attempts`或平台最终只有一条记录：前者先于平台调用递增，后者受幂等去重影响。复用`check-recovery-continuation.mjs`已有queryProxy的透明转发/请求记录接缝，仅按目标query统计请求；不复制它的丢包、重启场景，不新增产品计数器或代理服务。

- **续租条件：**同owner/epoch且未过期可续；过期或换代不可续，验证新增续租操作的真实WHERE条件。
- **事务交接：**仍有效但余量已减少的原领取，经`begin_submission_in_tx`所在事务成功提交后，租约按数据库刷新时刻加同源15秒重新设置，owner/epoch保持，计数仅按原动作推进。过期或换代领取拒绝交接，事务失败，不留下该次新增提交计数或有效平台动作。会话锁回归可能在漏掉该刷新时仍通过，因此不能替代此项。
