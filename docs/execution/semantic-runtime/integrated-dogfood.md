## 目标与边界

证明一般流程可用：资料同步→原文/整理→检索取证；用户多轮→澄清/SQL→明确执行→结果/答案→历史复用。通过的单位是实际场景及其证据，不是“所有功能已完成”的口号。

复用 [语音座舱试用包](../../dogfood/cockpit/START.md)、manifest、scenarios、既有100项与独立参考。公开合成资料仍是语音链路，不回到旧零售样例，不凭记忆补业务定义，不引入公司信息或原始音频。产品中不得写特定案例名称/答案/固定调查策略。

**已发生问题不因选样而消失。** 历史PoolTimedOut与S05首次失租分别有限复核；准备期租约缺陷及首次冻结回执已有对应修复，按CURRENT核对适用性，不再重复当成未修项。无法追溯的历史因果如实记“有限复核完成，根因未确认”，不无限追加试验、不改旧失败。当前必要路径仍失败则继续阻断；若全部核心出口满足、仅剩既有API阻断的历史因果无法追溯，按核心修复包第4.3节给用户具体遗留选择，不自动豁免。来源过宽仍须修复/复验，资料前提不足则按原许可核对，不改题刷分。一般质量问题按根因集中处理，非阻断缺口如实报告。

## 执行顺序与方法

1. **先复用已有证据。** 核对版本、环境及实际变化影响，列核心表中的已证明/待补/阻塞。来源和参考未变时不重跑`verify-cockpit`、`verify-fixture`和参考构建。通过记录只支持原覆盖范围；有相关代码变化必须判断是否需要复验，不按时间新旧简单作废或照抄。
2. **完成不依赖故障端点的部分。** 补核心UI、权限和受影响工程证据。数据库harness及共享结果写入串行，不靠多个进程同时改同一个结果JSON提速。继续使用本轮固定库、集合、账本和语音资料，不重新建千表库或索引。
3. **恢复后跑真实核心流程。** 沿已有费用与端点授权；真实配置使用request/data、v2/latest_only及当前容量。供应商500/503时暂停受影响的模型试用；有新恢复依据后只做一个原核心场景代表，成功才扩展。旧S06等非核心失败不再作为反复探测端点的题目。保持24次/消息、连续临时失败3次，不新增套件累计门槛或逐批审批。
4. **依次补S01→S02/S03、T02→A03、J01/J06/J19及来源原轨迹的缺口。** 核心表里已通过且仍适用的记忆、Skill和资料样例不重发。无需先刷完P01–P09全部问题再启动主流程，也不自动进入其他L1–L6题目。只发送原消息；没有本题真实草稿时不发执行消息。
5. **按原因修复，按影响复验。** 阻断核心路径或已证实的权限、明确来源、执行授权、数据完整性问题立即处理受影响链；其他独立核心项继续。一般表达质量集中记录和修复。在连贯修复边界统一独审/验收，不每题开新包；仍在主09范围的小修不另起业务增量。Rust未改不重建，正式冻结期间不改输入，通过后没有相关变化不重跑。

已有发送脚本支持指定case ID；使用现有入口即可，不新增调度器或评分平台。结果的行数、数值和单位尽量用现有`grade.py --reference-key ... --actual ...`及独立参考核对，列映射需可审查；该命令不能判断解释、来源和授权是否正确。操作者重点看这些语义判断及最终用户体验，而非每次重读全部日志。已有采集器会按多轮重复读取同会话记录/结果；优先复用已保存产物，只有证实采集耗时影响推进时才作局部优化，不为此暂停验收重写工具。

执行、业务判分、修复分别记录。同一次运行结束不等于通过；修复前后用独立attempt，不替换旧输出。全部原失败、unknown、usage、预留和费用保留，不换ID补额或重发未知操作。

## 本轮后置范围

## 证据与收尾

原100项沿用 `records/results-template.json`，十条轨迹单独用 `trajectory-results.json`，均在 `.local/dogfood-runs/<run_id>/` 保存。继续保留100/10完整分母，未跑后置项保持not_run，已发生的fail/partial/blocked保持实际状态，后置理由写现有报告；不新增deferred枚举或给未测项填pass。原grade默认行为不变；仅按核心修复包第7节增加固定核心项必须pass的可选检查，不修改原断言或自动语义判分。没有该选项的记录完整性校验仍允许not_run，两份记录校验通过不能代替核心业务通过；最终还须对应真实证据和独审。另在现有报告按核心表逐能力说明证据和缺口，不另建评分系统。保存实际输入、SQL/参数、工具/输出引用、模型请求边界证据、关键截图和每次attempt。授权配置与凭据不进公开记录。报告按根因聚合，重试成功不删除失败尝试。

全部D01–D18、C01–C08、A01–A10在轨迹清单的`requirement_coverage`对应到原case、综合轨迹或工程检查，原100项均有需求归属。映射不代表某条轨迹覆盖整项要求，仍需核对各子行为及相应证据；D18邀请/发布保持后置。复用历史工程证据时注明指纹和本轮适用性；当前真实模型/界面观察必须来自本轮。

需要的性能只记录实际小/大目录、候选/回源工作量、延迟和覆盖限制；不建设新的观测平台。真实模型、合成平台、真实数据平台各自写明；真实平台不在本轮实现范围，不能因此谎称已接入，也不阻止说明合成环境已验证范围。

千表表示预先准备的检索底库规模，查询应按相关性选取内容；全量初次索引/显式丢库恢复与单次检索分别记录耗时和工作量，不能把三轮索引建设耗时当作用户查询耗时。无需为纯Node校验或答案组合反复建立千表库；尺度与复杂恢复场景保留在回归库，核心所需工程证据按实际影响复用。不修改输入/断言来加速通过。套件时限与单次产品期限分开，环境失败先定位再决定受影响复跑。
