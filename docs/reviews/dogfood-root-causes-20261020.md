# Dogfood 问题根因复核

复核对象：`flash-r1` 原始失败和部分完成项，以及修复过程中发现的共用缺陷。实现基线为 `c9d0ced`；本记录说明根因和证据边界，当前进度及有效验收以 [CURRENT](../CURRENT.md) 为准。原试用账本没有改写，也没有将工程夹具的通过计入真实模型正确率。

## 原试用发现

| 发现 | 核实的原因 | 修复方向与证据边界 |
| --- | --- | --- |
| ISS-01：歧义口径被当作用户选择 | 唯一命名指标不等于用户已选择分母；原工具没有显式表达这次口径决策。模型仍可能遗漏歧义 | 可选 `semantic_resolution` 表达解释、依据和未决差异；已声明未决时在旧稿失效及平台编译前拒绝。完整真人原话防止截掉否定。该校验不证明模型发现了全部歧义，真实质量仍有缺口 |
| ISS-02：独立问题合并、部分回答丢失剩余问题 | 单一顶层问题不适合独立可答的多个决定；多题任务的启动快照只带首题却没有省略标记；模型也会新增重复问题或改变候选含义 | 支持各自有 ID 的 `clarifications`，只关闭指定已答 ID；未答项保持。启动快照明确未交付全部问题，沿现有工具补读。真实样本已见部分回答正确保留，但澄清收敛与候选忠实性未全部通过 |
| ISS-03：两条已明确授权的 SQL 被要求重复授权 | 指令把逐条执行授权表述得过于机械，未清楚区分已展示的多条 SQL 与新生成 SQL | 一条完整真实请求可覆盖用户明确列出的多条 SQL；各 SQL 仍按自己的版本和任务授权。真实定向样本完成两条合法提交；不是放开任意新 SQL 执行 |
| ISS-04：明确拒绝后不恢复 | 工具错误仅给模型 error/hint，丢失完整 recovery；`route` 成功后仍遗漏原 `execute_query` | 完整恢复数据进入 Pi，区分消息归属修复和实际执行回执；真实样本已完成拒绝后的原动作。`unknown` 继续按原身份查证 |
| ISS-05：工程夹具失败 | 平台版本写死，与真实初始版本冲突；正式回答测试依赖提示短语而非行为 | 从真实版本推进，保留同版本冲突负例；正式回答按工具前后文字、持久化与刷新验证。未改原业务期望 |
| ISS-06：草稿被说成已提交 | 嵌套 `get_query.data.query` 没有替换旧工作区观察，模型还会混淆保存与提交 | 按真实回执结构撤下旧状态，给出状态含义。最终文字仍由模型生成，宿主状态正确与模型遵循分别验收 |
| ISS-07：等待澄清被误报版本冲突 | 任务状态守卫把等待、取消和版本错误合用一个错误码 | 分别返回 `waiting_clarification`、`task_inactive`、`version_conflict`、`clarification_not_open`，让合法恢复有明确前提 |
| ISS-08/09：跨任务、跨条件报告保存失败 | 原设计只允许当前同任务条件，拒绝本身符合旧契约，但无法完成用户的组合分析目标 | 报告容器与每份来源身份分离；同一本人会话内可组合 1–5 份有效依据，每份保留原任务/条件/查询/结果。历史读取不夹带当前正文，任一来源失效整份隐藏 |
| ISS-10：补写资料未定义的业务规则 | 模型把未声明的状态关系、必要条件推成充分条件或肯定/否定结论 | 资料定义与推断边界已明确；没有引入写死业务答案的判断器。真实样本部分改善，尚不能宣称该类语义错误消除 |
| ISS-11：没有定位指定资料却声称读完 | 指定文档自身没有显式业务域，域筛选正确排除；录入/编辑 UI 缺少补齐业务域的入口，模型又把近似资料当成目标 | 补齐对象与章节的显式业务域维护；范围贯穿检索，不继承关联表的域。既有未标域条目需要维护者明确补齐，不能批量猜测归属 |
| ISS-12：回答自行补算，SQL 缺用户所要比例 | 真实模型未稳定遵守计算应由 SQL 或对应宿主回执完成；有工具能力不等于模型会正确使用 | 精确 figure 引用仍由宿主核对；当前完整 Flash/off 样本仍出现 SQL 缺比例、文字补算和错误分组解释。该项保持失败，没有用数字碰巧正确来放宽要求 |
| E11：资料选择器看不到第 100 条之后 | 前端忽略 `next_after_id` | 补分页、去重、选中保留、失败重试和迟到响应隔离，覆盖实际后页选择 |
| Z05：保存报告疑似改变阅读位置 | 原驱动没有区分真实内容前提及浏览器滚动状态，未能证实产品缺陷 | 使用有效来源和受控异步事件验证锚点/焦点/草稿与底部跟随；不为驱动误判改动对话滚动实现 |

## 重新审查发现的共用根因

**持久正文的来源不能只依赖模型填写的引用。** 宿主已经记录了实际交付给模型的资料，但任务、条件、SQL、依据、报告标题、记忆及 Skill 草稿曾只保留模型显式引用。漏填引用后，来源失效引发的第一次上下文重建是正确的，下一轮却可能通过持久对象再次读到旧内容。跨轮及跨会话合成反例证实了这条路径。

修复复用既有 authority 记录，保存宿主实际来源并集，并在写入、读取、列表、重放、采用、派生和发布副本时核对。直接选用的 Skill 与作为出处的 Skill 分开，避免要求接收会话再次选用祖先 Skill，也避免把出处当作可执行指令。跨会话查询出处仍核对本人、空间、原会话状态及完整来源。旧格式或来源不完整的生成正文保留记录、隐藏内容；同文重传、清引用、修改无关字段和启停不能解除来源；人工入口真正改写相应字段可建立人工来源，模型改写则继续绑定宿主当时的完整来源。

这是一种保守的来源保护：来源并集不能精确证明某句话实际用了哪份资料，因此撤回其中一份资料可能隐藏更多生成内容。人工独立录入与模型生成字段分别处理，保留人工资产修正显式依赖的能力。发布独立副本也不自动授予接收者读取其上游私人资料的权限。

交叉审查同时核实并处理以下相关问题：

- SQL 外发检查和旧稿失效发生得过早；现在先核完整运行及条件来源，提交事务内再核。
- 当前运行有效、但所访问旧正文失效时，拒绝没有持久收尾，遗留 `prepared` 工具；现在区分目标拒绝和整个运行上下文失效。
- 成功 `validate_sql` 的重放曾永久复用带正文的旧诊断；改为与其他只读工具一样重新核验。
- 系统结果唤醒不能作为保存、修改或停用个人记忆的真人授权。
- 当前任务目录、资产维护影响目录、查询 UI、旧成功回执和新控制事件都需要相应内容投影，不能只保护主读取接口。
- Mem0 正文来源校验不能阻止停用/删除清理。清理使用原作业身份与受控空正文；发送内容建索引及付费回调仍核验来源。
- 实际模型工具 Schema 的注释裁剪曾误删业务 `title` 字段；现从投影后的 18 个工具验证字段及正负例。
- 旧资产来源的恢复曾直接跨模块读取工具账本；现由用例组合资产和运行模块的公开接口，只物化相同资产版本下缺失的来源元数据，不覆盖已有来源或并发新版本。
- 依赖格式变更必须让旧检查点失效；同一未完成输入不能换身份或预算重做未知操作，Worker 也不能把所有领取拒绝伪报为重试耗尽。

## 证据解释

新回归覆盖真实 Rust 事务、MySQL、Pi 检查点、合成执行平台、受控 provider 协议及浏览器。它们证明指定边界和用户操作，不证明真实模型的自由决策质量。测试命令、最后运行结果与独立审查入口由 CURRENT 统一记录。

真实 Flash/off 的完整贡献链和独立澄清样本仍保留失败：有正确的状态持久化、执行恢复和查询结果，也有重复澄清、未登记提问、未经确认的默认、非 SQL 输出的派生数字及无依据解释。继续用相同配置重复抽样或追加提示词，不能提供充分的根因证据。

用户随后批准一次 Flash/high 对照，总限为 24 次调用及 0.50 美元。实际请求确认启用了 high；最终 24 次（22 次普通请求、2 次 Pi 原生摘要），账本费用为 175317 微美元、预留为 0，触达调用上限后停止，默认模型未变。新证据区分如下：

- 设备验收说明样本正确保留未定义分子及状态关系，没有将未知写成已知；仅证明该输入的单次表现。
- 两个独立目标分别登记，模型先调查资料，但仍把复购分母与分子判定合为一题。用户只答分母后关闭复合题、另建分子题，待定分子没有丢失，也没有擅自写 SQL；这是独立问题语义契约未稳定遵循，不能夸大为新增授权或默认执行。
- 贡献 SQL 已含差额、合计、比例，离线只读计算与独立合成参考一致。但最后一次提交后用尽试验总调用数；查询只确认排队，诊断脚本未恢复平台 Worker，没有正式结果解释。不能据此关闭自行补算、错误 SQL 解释或原完整多轮分析问题。
- 实际 provider 请求包含完整原题、用户原话和相关工具规则，至少这次复合提问不能归因于上下文漏给；一次高档表现也不能证明所有剩余问题都由模型档位决定。

对照还确认两处工具契约的多余负担：已有任务只改条件却强制重传 `goal`，以及执行工具已明确指定查询却必须先单独 `route` 同一任务。修复让已有任务省略目标时保留原目标及来源，并仅在当前消息无任务关联时将具体执行目标登记与确认合在同一事务。已有目标不匹配、其他待处理消息、权限、版本、澄清、未知结果及预算检查保持。两项属于一般工具易用性修复，不等于复合问题或最终回答语义已被程序证明；新接口的验证另记，不把之前的 high 运行当成修改后真实通过。

对照原报告与独立审读分别为 `.local/checks/reliability-flash-high-comparison/report.json` 和同目录 `high-review.json`。诊断报告遗漏了失败轮及 `error.code`，已通过保留的隔离数据库和 Pi journal 补证为 `model_budget_exhausted`；该消息只用了 5/24 次，其余调用属于本次试验的其他消息。直接调用 `deliver`、暂停 Worker 后关闭 harness 留下的运行中记录，不能作为正常服务错误收尾缺陷的证据。

重新审查还用原渠道 SQL 加入 NULL 渠道构造了独立反例：`GROUP BY` 保留 NULL 分组，来自同一组渠道的差额求和仍等于其总计。因此“NULL 渠道可能导致两者不等”的文字解释确实不成立。两个完整失败运行的系统提示与本次审读版本相同，已明确要求计算来源和澄清登记；但当时完整 provider 请求没有保存，工具 Schema 又有后续变化，现有证据不足以排除所有上下文或协议因素，也不足以认定模型本身是唯一根因。多题启动省略是新证实的程序缺口，其修复效果与其余语义质量仍须分别验证。

本轮接口修复后的64KiB压力回归另外发现固定内容的容量回归：新增说明增加766字节，Pi已经正确识别超限并摘要历史，但固定规则、完整工具和启动事实不会随历史摘要缩小。实际拒绝请求为65634字节，仅剩摘要与当前工具组，无法再靠摘要移出该固定开销。修复只归并重复的执行归属、授权及goal说明，减少529字节，保留全部Schema和Rust约束；原完整长短历史回归通过，最大65185字节，29次本地调用含15次原生摘要。没有扩大64KiB或裁减输入、回执，不宣称任意长输入都能容纳或摘要更少。原失败、逐请求诊断及独立复核均保留。

追加修复已通过514条同源契约、13组澄清专项、12组聊天执行专项、独立事务回滚与未知回执探针、实际工具投影、发送前体积守卫、原生压缩及锁序检查；这些检查均为本地受控模型协议。当前仍需真实模型检验独立澄清和完整结果解释，整体审查未通过，也没有提交、推送或更新常驻服务。

## 取消累计测试上限后的真实复验

用户更正后，采用现有 `budget_mode=request`，不设测试累计调用、费用或到期上限，每次用户交互仍保持24次及连续临时失败3次停止。当前源码的三个固定流程已完成，共41次调用、预留0，每个消息预算最多7次；查询结果唤醒与原执行消息共用预算。未修改产品限额、默认模型或常驻服务。

普通歧义问题本次自主识别口径差异，持久登记问题并等待，没有生成或执行SQL。原趋势到贡献五轮已取得两份真实合成平台结果和正式回答：实际金额与贡献比例均对应SQL列，没有再自行补算缺失环比。它们是本次固定样本的改善，不能抹掉历史失败或推定全部模型输出正确。

独立审读仍确认以下缺口：

- 复购定义与分母人群可以独立组合，模型却将它们配对放进同一个问题。只答分母后关闭旧题、另建分子题，未丢剩余决定，但旧问题的`resolved`状态不准确。退款率的订单/金额/客户三种指标类型本身是一个合理的口径选择，不能仅凭出现“分子/分母”字样判成复合题。
- 贡献SQL的明细使用`NULLIF`，合计比例却固定为`100.0`。独立SQLite内存反例中，两渠道分别增加100、减少100时，明细比例为NULL，合计仍100%；空数据时金额均NULL，合计也100%。当前种子总差额为21000且结果正确，不能因此放过可复用SQL的边界错误，也不能手工改这份SQL冒充Agent一般能力已修复。
- 正式答复把已经计入冻结快照的退款写成仍可能调低本次结果，又从两个月的渠道金额判断“不是单一渠道异常拉动”，没有异常基线支持。普通答复还展示了内部任务、查询ID及条件版本，属于较低优先级的输出问题。

原试验脚本对“全会话只有一个草稿”的假设过窄：模型在解释趋势时另存了未执行的环比补算稿，随后又保存贡献稿。原机械失败保留；续接仍使用原trial、数据库、会话与平台目录，只发送原流程尚未发送的第5句，按新增查询差集等待精确贡献查询的结果。没有重抽样、换预算或改写原报告。

当前证据分别为 `.local/checks/reliability-flash-high-remaining/report.json`、`.local/checks/reliability-flash-high-contribution-continuation/report.json`、`.local/checks/reliability-high-clarification-semantic-review.json` 及前者同目录的 `trend-contribution-review.json`、`contribution-boundary-probe.json`。实际provider请求已保存，排除了本次规则未送达、累计预算中止和结果未交付三种解释；尚不能据此认定所有剩余问题只有模型能力一个根因。当前仍不宣称全部修复完成。


## Pro/high同题对照与新并发根因

用户批准的两条原流程共7句已完成，累计35次实际模型调用、1177848微美元、预留0，7个原消息scope最多8/24次；累计试验次数、费用和到期字段为NULL。默认模型及常驻服务没有改动。完整付费流程使用相同冻结代码、工具与资料，后续工程修复不追认成这次真实模型的修复后通过。

独立澄清两轮中，Pro起初就将复购分子与分母登记为不同问题；只回答分母后，原分母ID关闭，分子及退款口径的ID、正文和选项保持开放，没有SQL或执行。相比Flash同题本次更好，但不能由一个样本推定所有独立澄清稳定正确。

原趋势到贡献五轮取得正确月度/渠道金额与差额，初稿的SQLite排序语法拒绝后也成功修订。不过正式回答仍存在以下实证问题：

- 月趋势回复给出SQL未返回的11000/21000分差值；贡献回复给出100%/52.4%/28.6%/19.0%，贡献SQL实际只有渠道、二月值、三月值和差额四列。数字算对不改变当时缺少受控计算来源的事实。
- 无资料支持“1–2月基本已沉淀”的退款成熟度；还把SQL保留`is_test=0`与正付款额写成排除，SQL本身正确。
- 贡献SQL没有比例列，因此零差额内存反例只能证明金额守恒，不能把没有计算比例当成比例除零已修复。空数据返回NULL聚合值。

实际正式生成请求保留完整系统规则；原SQL和rows/附带statistics也完整交付，未由接入层删掉差值、比例或换算列。原样例允许人类阅读时换元，与本次明确分存在材料张力，但不能解释无来源差值/比例；没有修改样例或独立答案来取得通过。后续Pi摘要有沿用先前错误结论的现象，首次补算却发生在该摘要之前，不足以认定摘要是最初根因。自由聊天正文目前没有逐数字来源验证；保存依据的figures只保护明确引用的单元格，不证明整段文字。仅靠正则过滤或强制保存依据不能补齐这条语义边界。

对照同时暴露了一个独立的工程问题：同一结果唤醒的助手响应并行调用同一查询的rows和statistics，rows成功而statistics持久拒绝为`stale_context`。Pi1.3默认批内并行，宿主工具却会修改同一run的结果来源清单；先完成的工具扩展清单，另一工具最终核验时所持快照已经过期。实际日志没有保存逐行事务交错，不能把代码路径推导当作完整DB调度重放；真实SDK配合受控宿主边界的确定性测试复现了自冲突。

修复给所有宿主工具声明Pi原生`executionMode: "sequential"`，同一响应仍能合批，Pi按模型给定顺序执行。严格的最终快照检查、权限、版本、原操作身份与预算保持；不新增宿主调度器，不强迫每个工具增加一次模型往返。代价是同批工具的外部耗时相加；不同会话及后台查询仍可并行。基础建任务工具遵守相同顺序约定，但不宣称它的独立事务路径也发生了相同来源自冲突。

主脚本保留了“两个未提交新稿”的包装器失败：其中一个编译拒绝，另一个才是可执行修正版。续跑按编译通过、待确认及未提交共同定位，在原数据库/trial/会话/平台目录只发送尚未发送的第5句，未重跑前四轮。证据为`.local/checks/reliability-pro-high-comparison/report.json`、`reliability-pro-high-continuation/report.json`，独立审读为前者同目录`clarification-review.json`与`trend-contribution-review.json`。并发修复证据由CURRENT汇总，整体仍不宣称全部问题已解决。
