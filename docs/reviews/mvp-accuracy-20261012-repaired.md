## 评测要回答什么

程序检查回答流程是否遵守契约：条件有没有保留，旧SQL能否被误执行，个人偏好是否只属于本人，查询结果是否回到原任务，模型用量是否完整入账。

内容复核回答业务结论是否正确：SQL在独立种子及数据变体上是否算对，文字解释与加工规则是否一致，资料缺失有没有明确留下。字段预填按完整场景判分，初次与再次预填均须正确；结构合法、引用存在、人工值保留不能代替内容正确。

这些场景使用从零构造的合成材料。通过它们能证明特定口径与失败边界的行为，不能外推真实企业数据、多租户容量或任意自然语言问题的准确率。

## 三次中断分别是什么原因

### 首次：SQL与任务条件的时间表达不一致

原始测量见[第一次报告](mvp-accuracy-20261012.md)。S03先查询2026年1月净收入，再补充app渠道。两份SQL使用完整UTC月区间，独立结果为12400分、1600分及各5组变体一致；任务记录却保存 `2026-01-01` 至 `2026-01-31`。原UTC条件断言失败，剩余13题未运行。

共享Schema此前仅把字段限制为字符串，缺少格式约束。修复将 `Conditions` 与 `ConditionSet` 的时间明确为UTC完整时间戳：起点包含、终点不包含，整月终点是下一月起点；业务时区另存，未知边界仍可为null，清除用unset。Node与Rust均执行同源格式及日历合法性校验。宿主拒绝含糊日期，不自动猜时区或修改旧数据。

新增反例先在旧实现失败，修后271条跨语言契约通过，生命周期、请求时钟和聊天执行回归通过。随后真实S03小样完整完成：旧稿确认被拒绝，新稿执行为1600分并解释为16元，10调用、估算US$0.052410、预留0。小样不算正式成绩。

独立代码审查另发现升级恢复影响：已提交但缺少Pi工具结果的旧格式调用，可能先被新Schema拒绝，接不回持久回执。修复沿用原登记和执行入口：先核对当前运行权限及原参数指纹，接回确定回执，再对真正的新执行校验当前契约。只在登记阶段明确拒绝时返回可修正的工具参数错误；已登记却没有确定回执的旧调用返回 `outcome_unknown`，不告诉模型“未执行”，也不修改历史日期。独立12项纯内存分支检查通过；带MySQL的恢复回归9/9、权限回归5/5通过，均未调用真实模型。旧日期、操作标识、原始运行、参数指纹、回执与副作用次数保持，失效资料仍不能经恢复重新进入模型。

### 第二次：验收器把等价告知判为失败

时间修复后的正式轮通过S01–S05、B04的机器检查，在B05中断。模型答复为：

> 同时把“默认只看web”记为你的长期偏好（仅影响以后的分析，不改变本次口径）。

脚本只匹配 `/保存|记住/`，没有接受这句话。独立复核确认个人资产回执成功，归属Alice、personal、enabled、version=1；正文与范围包含web默认及本次全部渠道例外，`memory_saved`事件与资产ID一致。当次SQL没有渠道过滤。

原B05要求成功保存并告知、之后新会话采用、停用后不采用，没有限定这两个词。因此只补入 `记为(?:你|您)的长期偏好` 这一限定等价表达，保留持久资产、独立SQL、跨会话、修订、停用及保存失败断言。原句修前失败、修后通过，另3个正例和3个缺告知的反例通过。内容准确性仍交独立复核，文字正则不替代回执。

这次中断轮共58调用、估算US$0.368563、预留0。B05的跨会话及后续步骤尚未执行，不能计为整题通过；余下9题没有运行。旧证据保持原失败状态，后续使用固定修复版本独立测量，不拼接两轮成绩。

### 第三次：正确的匿名边界列未被核算器识别

恢复修复后的完整轮在S02停止。SQL输出 `paying_customers_known`、`anonymous_paid_lines`、`unknown_boundary_present` 三列，种子结果为 `[5,1,1]`。核算器支持匿名存在标志，却只识别 `has_`、`any_`、`exists_` 前缀，因此返回 `expected_rows=null`，并非算出了不同人数。

独立内存SQLite核对原种子和7个变体均正确。只新增这个明确别名到既有 `anonymous_present` 角色的映射，仍逐列核算；新增1正例和4反例，恒定1、订单数冒充行数、未去重、重复角色均拒绝。该轮11调用、US$0.060963、预留0；确认执行与解释尚未进行，S02仍为未完成，其他14题未运行，原件保留。

### 后续采用隔离单次采集

连续fail-fast未能取得全16题产物，反复从头测量既浪费调用，也无法描述后续题目效果。最新套件预先固定原16题，每题各用独立干净的合成fixture和账本，完整场景执行一次；单题失败保留后继续，不挑历史成功题、不对同题补抽。多轮记忆与查询交互仍在各自题目内部完整执行，题间不共享残留。

同一套件的输入指纹与模型配置必须一致，费用从修复阶段总预算逐题扣除。未知费用、账本不完整或原件损坏会先归档再停止；普通断言失败不会阻断下一题。最终以16题为分母，机器失败或内部步骤未完成的场景计为不通过，明确说明原因；“全部已尝试”不等于16题均通过。

原隔离采集确实在P03停止了：初次分析返回，内部复核调用未得到确定回执，预填为 `unknown/model_unknown`。只读查证确认2次调用中1份已结算US$0.027955、1份仍为 `issued/usage=null`，占用原预留US$0.049152。运行进程及测试Worker均已退出。不能把该调用当作未收费或成功，也没有证据把它确定归因为某一种网络故障。

之后明确修订采集方式，只首次运行尚未尝试的P04/P05。P03原件、数据库及原停止manifest保持不变，未知预留继续全额占用预算；后续两题固定同一产品指纹、模型和业务标准，按已结算金额加全部未决预留扣减余额。后续再出现未知则停止，不重试P03，也不重抽其他题。原协议的“全部费用已结算”条件没有满足，最终报告将场景采集与费用结算分开。

## 当前固定套件已确认的问题

- S02附加的 `paid_lines` 是全部支付行数，当前核算器没有该列角色。独立内存计算原种子与7变体均相符；本轮保持原件失败，不再修改核算器或补抽，确认执行与最终解释未验证。这是验收覆盖不足，不能称为SQL数值错误。
- B07知道缺少购买时地区，却未先取得用户接受替代口径，就生成当前地区SQL。任务进入等待确认而非等待澄清；查询尚未执行。因此错误是跳过口径澄清，不能表述为擅自执行。原B07要求先说明历史缺口、给出当前快照选项并确认意图。
- P02的流程、引用和人工保护通过，但初次声称“无成功事件，或只有成功退款”时 `paid_at=NULL` 并写入目标表。独立内存执行原始schema/ETL：只插入成功退款100分、无付款，得到paid=0/refunded=100，违反 `refunded_amount_cents BETWEEN 0 AND paid_amount_cents`，目标表仍0行。属于实质内容错误；字段可空不能证明整行可写，未以再次预填正确覆盖第一次错误。
- P03的初次分析有草稿，内部复核却为 `issued/usage=null`，预填 `unknown/model_unknown`；初次未成功，人工修改和再次预填未执行。按完整场景计不通过，类别为模型调用结果未知，不能据此声称草稿已交付、人工保护已验证或具体网络根因已查明。
- P04两轮都正确解释了quantity、下单件数与缺少退货件数，人工保护通过；初次没有覆盖原题required_facts[1]要求的 `(order_id,line_id)` 唯一标识事实，正文和全部引用均无主键/唯一性。再次虽已补齐，原验收要求两轮均正确完整，因此计为必需事实遗漏。它不是数量求和错误，也没有因为初次 `gaps=[]` 扣分：正文已明确退货件数未知。

- P05两轮正确解释了整单状态、部分退款仍可能为paid，以及不能只筛refunded判断是否发生退款；但两轮正文与全部引用都没有给出原题required_facts[3]要求的“订单退款率包括部分退款订单”这一指标分子规则。属于必需事实遗漏，不能与错误计算退款率混称。

S01、S03–S05、B04、B05、B05-failure、B06、B08、P01的完整内容与行为已独立复核通过。查询独立变体、个人偏好web→app→停用、保存失败不采纳、旧查询结果归属均有本轮原件支持。P01两轮的事实、未知项、引用与人工保护通过。少量措辞问题仍保留在逐题报告，不能由流程通过推断任意问题都可靠。
