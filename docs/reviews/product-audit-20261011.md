# 产品、准确度与性能审计

日期：2026-10-11。审计基线为 `ba21773228e7a73cc69a655f0e46b40d2ea101f6` 加当前工作区已完成的 `I2-DOGFOOD-READABILITY` 修复。本报告是建议，尚未形成实施决定；最新状态见 [CURRENT](../CURRENT.md)。

## 结论

建议沿用当前 React、Rust、Pi SDK、Mem0、MySQL 和 Milvus 架构，优先改善三件事：**将真正相关的依据交给模型、减少用户等待、让用户能定位并纠正答案的来源。**

核心产品指标应是“用户不需要返工，就得到可信结果的比例”，同时记录完成所需时间。SQL 能执行、检索命中一个对象、记忆成功保存，分别只是中间环节。解释改变了时间口径、用户无法判断数据范围，仍不能算完整任务成功。

当前基础可继续使用：同一对话多轮、多查询、查询后台运行与停止、语义维护归属、明确共享纠错、Pi 续接和 Mem0 个人记忆已经有实现及定向证据。本轮不将这些能力重复列为缺失，也不重新打开上轮已修复的六项问题。

## 方法与证据边界

- 三个独立只读审计分别检查准确度、性能、产品流程；主审计核对实现、既有报告和实际页面。
- 实际打开当前语义目录、整篇文档、查询结果、查询依据、已有会话的 Skill 入口，并采集一个空闲工作台的网络请求次数。
- 复用当前增量已通过的验收，不重新运行整套测试；本轮没有新增模型或 embedding 调用，没有修改产品代码、配置或业务数据。
- 区分当前实测、当前代码确认、历史失败和待验证假设。没有进行生产并发负载测试、真实 Datasight 接入或全面安全审计。
- 同步缓冲区与来源同步更新继续暂停，不列入本轮方案。没有提交或推送。

| 3 | 减少空闲轮询、全量历史读取和流式输出重复读库 | 减少等待、数据库竞争和长会话卡顿 | 轮询当前实测；内部复杂度代码确认 | 小到中，分开交付 |

以上顺序表达产品价值，不要求一次全部实施。实现前应复用既有测试补一份当前版本的小批内容基线，作为改动是否有效的判断依据。

## 1. 检索找到了段落，交给模型的却可能是文章开头

**确认事实：**

- `crates/data-agent/src/modules/retrieval/vector.rs:200` 按 360 字符片段建向量。
- 同文件 `:158` 搜索只取对象标识、版本、类型，`:169` 去重后丢弃命中条目、段落位置及分数。
- `crates/data-agent/src/modules/retrieval/mod.rs:98` 最终摘要从每个条目的开头截取 600 字符，SQL 为 2048 字符。

例如，长文末尾才写“按付款月份统计，退款累计截至快照日”。向量可以命中这句话，工具给模型的初始摘要却仍是前面的业务介绍。模型可以继续分页补读，但需要额外判断和调用，也有漏读的机会。当前代码足以确认这条信息丢失路径；本轮没有测量它造成的最终错误比例。

**最小建议：**保留命中的条目与字符范围，回源验证当前版本和权限后交付相关片段，附完整章节入口；Pi 继续自主补查。不要将不同版本的片段直接拼接，也不要将相似度当作事实可信度。

**验收：**使用关键定义在长文后部、同名指标、相近业务干扰三类合成案例，分别检查目标对象命中、关键依据进入上下文、SQL 和解释正确。比较补读次数及耗时，不能仅以 Recall@K 提高宣布完成。

## 2. 语义目录整理之后，还需要让人判断内容的来源和维护状态

**确认事实：**没有人工覆盖时，模型建议可以成为 `effective_value`，其状态为 `unverified`（`knowledge/store.rs:520`）。页面默认只对 `needs_review` 提示“依据有变化，请核对”，正文附近不区分 `unverified` 与 `confirmed`（`KnowledgePage.tsx:114`、`KnowledgeEvidence.tsx:25`）。来源详情虽可展开，但用户要主动逐项查找。

这不是要求所有内容先人工批准。自动整理让存量表快速可用，但用户应知道眼前内容是平台资料、模型解释，还是人工维护内容。

**标签必须准确：**当前 `confirmed` 在人工录入或保存路径写入，没有独立验证正确性的程序，因此宜显示“人工维护”，不能显示“已验证正确”。`unverified` 也可能是平台事实或合成资料，不能全部叫“模型建议”。

**最小建议：**

- 结合已有来源、建议和人工覆盖，显示“来源资料”“模型整理，尚未人工维护”“人工维护”；来源变化另标“待复核”。
- 在现有目录提供待复核/待人工维护筛选，帮助负责人找到工作，避免逐表展开。
- 先核对实际常用指标的行粒度、时间字段、公式、关联、单位和未知范围；维护收益应按影响的分析任务判断，不追求填满所有表单。

**验收：**同一说明的不同来源状态能在语义详情和查询依据中直接区分；人工保存和来源变化后标签准确；保留自动建议可用、人工值受保护、共享修改需负责人保存的既有规则。历史预填错例及新的改写题一并复核。

## 3. 先消除已有链路的性能浪费

### 3.1 空闲会话每分钟约 260 次请求

当前实测：一个无生成、无运行查询、无交互的已打开会话，在 **31.875 秒发出 139 次 API 请求**，折合约 **261.65 次/分钟**。snapshot、queries、skill-selections 各 46 次，角色接口 1 次。事件未截断。此数值是单标签页短时采样，不代表并发容量或稳定负载性能。

原因与实现对应：`Workbench.tsx:115–130` 每 700ms 读取 snapshot 和 queries；`SkillSelections.tsx:18–38` 独立以同频率刷新，未选方法也持续请求。`read_conversation.rs:47` 的增量事件响应仍附带全部任务、运行记录，`queries/store.rs:41` 读取全部查询；相关读取持有会话锁。

**先做：**空闲退避、隐藏页暂停或显著降频；有相关变化时刷新查询和 Skill；无变化时保持前端对象；历史查询按页加载。评估只读路径的锁范围，保留必要的一致性与授权检查。

**验收：**用同一空闲场景和含 10/100 条历史查询的会话比较请求次数、响应字节、页面更新耗时。后台查询完成、停止、新消息、刷新恢复和权限撤回仍须正确响应。先建立可比较基线，再约定刷新时延，不能靠单纯拉长所有轮询牺牲实时体验。

### 3.2 长回复会不断重读已经保存的文字

`apps/agent/session/deliver.ts:196–212` 对每个 Pi 文本增量串行发一次内部写入。`runtime/outputs.rs:12` 每次追加先读取该次运行的所有旧片段，SQL 见 `runtime/store.rs:196`。

输出 C 个片段时，追加过程累计读取约 C×(C−1)/2 行旧片段；1000 片段为 **499,500 行**，另外还有最终拼装。这是代码推导，不能据此声称当前回复耗时主要发生在此处。

**先做：**短时间内合并展示增量；追加时只读取所需序号或最后序号，重放再按指定序号检查正文。保留序号连续性、幂等冲突和恢复语义，继续使用 Pi 的事件流。

**验收：**本地固定 100/1000 片段，比较数据库返回行数以及模型结束到最终提交的时间；增长应接近线性。重复片段、缺口、取消、恢复和最终正文一致性不能回退。

### 3.3 接着测量检索与长会话的累积开销

以下为代码热点，尚未测出当前耗时占比，排在前两项之后：

- `retrieval/mod.rs:5–56` 在排序时重复序列化正文、线性查找排名。先预计算每个候选的分数与 ID→排名映射，保持排序含义。
- `retrieval/store.rs:14`、`knowledge/store.rs:857` 多次扫描 JSON 正文。分开记录候选扫描、回源、排序耗时，再决定索引调整。
- `model_calls.rs:28,51` 两个模型准入阶段均核对累计依赖；`context_authority.rs:89` 存在逐对象来源和资产查询。可在每次校验内去重和批量读取，不能取消两阶段检查或使用会掩盖撤权的长期缓存。
- `QueryCard.tsx:90` 对每个成功历史查询立即读取结果，页面仅显示前 10 行。按当前可见范围加载历史结果，保留新完成结果自动出现、过期不自动重跑的规则。

旧千表报告中的耗时使用合成目录和协议向量，场景条件不同，不能与本轮空闲请求测量混成一个性能提升百分比。

## 4. 回执丢失时，重试需要接回原消息

**代码确认：**`Workbench.tsx:150` 每次尝试新建会话操作 ID，`:158` 每次新建消息 ID；消息成功后才更新当前会话和清理草稿。服务端 `receive_message.rs:35` 按消息 ID 接回原提交，换 ID 则是新消息。

若服务端已经保存而成功回执丢失，用户再次发送会登记另一次问题，首问还可能多建一个会话。可能造成重复模型处理；本轮未进行故障注入，也不能直接推导必然重复执行 SQL。

**最小建议：**保存一次发送的稳定会话操作 ID、消息 ID 和冻结内容；结果未知先核对或沿用身份重试。用户明确改成新消息后再生成新身份，保留并行编辑的新草稿。

**验收：**分别在会话创建提交后、消息提交后丢弃回执；点击重试及刷新后重试，最终各只有一个会话、一条消息和一个对应工作项。原测试的发送前中止不能替代这两个场景。

## 5. 同一长期对话需要能够移除已经选用的分析方法

当前页面只有“管理与选用”，没有本会话移除；接口仅 GET/POST，存储只插入或更新选中版本（`SkillSelections.tsx:41`、`apps/api/src/main.rs:128`、`assets/store.rs:244`）。本轮在已有个人 Skill 的真实页面也核对了这一点。

用户在同一对话从收入分析转到另一类问题时，应能停止沿用之前的方法。全局停用会影响其他会话；普通用户也不能停用他人负责的公共方法。

**最小建议：**“仅从本会话移除”，不修改资产本身。沿用 Pi 资源和业务有效性检查，不新造 Skill 系统。

**并发边界：**第一版可以在当前生成及其待恢复输入结束后修改选择，后台 SQL 继续运行。直接删掉正在使用的选择会触发当前上下文失效；需明确从后续分析生效，不追溯撤销已经生效的查询授权或重放旧操作。

**验收：**同会话选择 A/B、移除 A，后续不再提供 A；B 和其他会话不受影响；刷新、恢复保持选择；已授权查询的 SQL、参数、预算及执行次数保持。

## 6. 记忆的下一步是适用性与可追查性

### 当前确定的策略与尚未证明的风险

Mem0 `top_k=200`、`threshold=0.0`、不重排；返回资产 ID/版本（`apps/memory/service.py:161`）。启动上下文按召回排序后，还把其他有效记忆补入，最终取前 20 条，每条先展示前 600 字符（`personal_memory.rs:338–359`）。

权限、状态、版本、依赖回源已经有保护。这里的风险是**有效记忆不一定适合当前问题**：小记忆库可能几乎全部进入上下文，长记忆的例外条件又可能在后面。本轮没有复现错误套用，不能声称 Mem0 当前失效。

**最小建议：**沿用 Mem0，比较现策略与“少量相关记忆进入上下文、其余按需查找”，保留适用范围、例外和本次条件优先级。用 20/100 条合成记忆覆盖无关问题、近义指标、临时例外、修改、停用和知识改版，衡量正确采用与错误套用，不只看召回率。

### 用户需要知道这次回答参考了什么

普通回答目前主要是文本，没有与查询卡等价的逐回答依据入口（`AssistantMessage.tsx:3`、`packages/contracts/schema.json:469`）。后端已有记忆/Skill 读取记录（`data_tools.rs:355`、`personal_assets.rs:195`），可以复用。

建议增加一个默认收起的“本轮参考”，连接当前问题实际读过的共享知识、个人记忆和选用方法，便于进入原有纠错或编辑入口。必须称“读过/参考”，不能把读取记录当作模型实际采用的证明。私人资产只本人可见，旧回答展示当时版本及当前有效性。

这样，用户发现错了以后可以定位应修改哪一层；临时条件继续留在本次任务，个人习惯进入个人记忆，公共定义通过既有负责人流程更新。

## 7. 结果展示还应减少用户的翻译工作

实际结果仍直接展示 `paid_amount_cents`、`order_status`、`web`、`paid`。对数据开发可读，对产品同学仍需要翻译。`QueryResultsView.tsx:22` 只提供原列名与原值，没有可靠的业务展示信息。

**建议：**有确认映射时显示“支付金额（分）”“订单状态”等业务标签，保留原字段名便于追查；值映射与单位必须有依据，缺少时保留原值，不能让前端猜测。用一句紧凑说明展示本次时间、关键筛选、数据截止和结果范围，详细来源按需展开。

图表当前画前 10 行原值，不等于完整数据的渠道汇总或趋势。给出明确的明细预览含义；需要业务聚合时仍由用户的分析需求产生 SQL，遵守聊天执行授权。

**验收：**用户无需读 SQL 就能说清这批结果的时间、单位、过滤与完整性；原字段、原数值精度、NULL、SQL 复制、CSV 和过期规则保持。已有元/分双值样例可用于核对，避免重新搭建报表系统。

## 8. 用小批当前版本内容验收决定后续投入

目前没有统一的现行端到端准确率。旧 16 题的 12/16 是历史 Flash/high 基线；Mem0 对比完整场景两组均为 16/18；最新 Flash/off 是一个持续会话的五条消息。题目、版本和设置不同，不能合并分母或把新局部成功改写成整体通过。

复用已有 16 题和近期真实错例，补少量未见过的改写与反例；在当前默认模型、语义和记忆配置上固定一次小批运行。保留独立答案、输入与源码指纹，失败不靠反复重跑覆盖。无需先建设新的评测平台。

| 要量什么 | 判断方式 |
| --- | --- |
| 完整任务正确 | 找对且读齐依据，SQL/数值/解释一致；该澄清时澄清，不编造 |
| 产生可信 SQL 的时间 | 从发送到可用 SQL，另记查询执行与结果解释时间，分开模型和平台等待 |
| 用户返工 | 修正口径、追问补齐、重新生成的次数；区分主动探索与修复错误 |
| 错误但肯定的回答 | 口径不明或资料不足时仍给确定结论的比例 |
| 记忆实际帮助 | 应采用时正确采用，不适用时不套用；同时记录上下文大小和额外调用 |
| 维护效率 | 负责人找到并处理一条重要语义缺口所需步骤与时间 |

内容反例优先：跨月退款、订单与订单行、当前属性与历史属性、零分母、长文后段限制、同名指标、个人偏好与本次条件冲突。结果计数的既有修复保留；不扩建通用 SQL 语义证明器，不给 Pi 增加固定调查流水线。

## 建议实施顺序

1. **先收敛明确问题：**稳定发送重试、空闲请求减少、语义来源状态展示、本会话移除 Skill。每项独立验证，保持原权限和恢复边界。
2. **集中提高答案质量：**保留检索命中段落，核对高频公共口径，对齐 SQL 与文字解释；用当前内容基线判断收益。
3. **再调整记忆与规模表现：**小样检验记忆适用性，补本轮参考入口；按分段耗时处理检索和长会话热点，完善结果业务标签。

流式输出的重复读库已有明确低效路径，可以与第一批性能修复同做，但需要单独的恢复回归；更深的索引调整和准入批量化应按测量结果决定。

先让少量代表性用户完成高频任务，观察他们何时需要数据开发介入。真实认证、真实 Datasight 权限和执行适配仍属于正式接入的已知边界，本轮没有把它们当作新发现，也不改变同步讨论暂停的决定。
