# 个人记忆提取对比：独立设计与实现复核

日期：2026-10-05。审查者未参与产品及实验实现；本记录覆盖本轮接缝、评分与固定正式批次，不代表整个 MVP 的新完成证据。

## 当前结论

方案已固定为 9 个正常场景、3 个故障场景，每组两次。正常成功率分母为 18，故障处理另报；失败和缺回执不补抽。两组使用相同修复后的产品、Pi SDK、Flash high、合成材料和业务约束。该范围可比较受控个人记忆的提取与复用，不能代表大记忆池或任意聊天自动长期化。

**下面两处接缝问题已修复并复核，固定正式批次和独立内容审查已完成。** 代表小样验证了接入与并发隔离；正式正常场景完整成功率均为 16/18。记忆管理与 SQL 的分项结果不同，见下文。失败、缺失与未触达故障均保留，未改答案或补抽消除失败。

### R01：不同工具调用共享候选标识

`experiments/mem0-comparison/agent-comparison.mjs` 的提取键只包含 message/action/asset/version/quote。两个独立 `save_memory` 调用若引用同一原文，会重用同一组 Mem0 IDs；`agent-memory-service.py` 将其绑定到不同资产后，搜索映射只能保留其中一个，停用另一个还会删除共享向量。

离线复现：同一 prepared operation 分别提交 `first-asset`、`second-asset`，搜索仅返回后者；随后停用前者，后者虽仍是正式有效资产，搜索结果变为空。

修复要求：使用宿主绑定消息和 SDK 工具调用身份区分独立操作；同一 SDK 调用在登记、执行、拒绝查询及恢复时重放同一结果。每个正式资产必须具有独立索引归属。

复核：当前提取键使用本次 `run_id` 和 `sdk_tool_call_id`；服务拒绝将同一候选绑定到两个正式资产。新增不同资产共享候选的拒绝回归通过。该实验只恢复尚未开始的组合；活动工具在新 run_id 下恢复不在本轮验证范围，不能据此声称已验证原操作身份跨运行恢复。

### R02：未提交候选占用检索名额

`agent-memory-service.py` 当前先检索所有同用户记录的 top 20，再剔除未提交候选。未提交候选即使不直接采用，也能把正式资产挤出结果。

离线复现：1 条已提交记忆、21 条排名更靠前的 pending 候选，得到 `accepted=0`、`excluded_uncommitted=20`。正式记忆很少并不能消除该问题，因为一次学习中的引用纠正可留下多个 pending 候选。

修复要求：在 Mem0 排序之前限制为已提交候选；仍需保留结果 ID、正式版本和受控读取校验，并在真实小样中核对后端收到过滤条件。审查中曾建议 metadata `in` 过滤，后核对 Milvus 适配器发现该建议不可用：`Memory.search` 上层会保留 dict 条件，而锁定 `milvus.py::_create_filter` 只接受标量。该建议已撤回。可在正式提交后合并更新候选 payload 的提交状态，再用标量状态过滤；具体接法需由修复与真实小样证明。

复核：prepare 标记 `commit_state=pending`；正式提交后通过 SDK `vector_store.get/update` 保留原 payload 并设为 `ready`。检索的向量与关键词两条后端路径均在排序前收到 `commit_state=ready`。21 条 pending 不能挤掉正式记录的回归通过；真实小样中 5 次来源边界被拒的候选未成为采用结果。

## 已核对的正确边界

- Mem0 提取输入为原始宿主消息及原文引用，不接收 Pi 生成的 name/body/scope；确定性合并多条提取结果，不按答案挑选。
- `run_id` 隔离提取阶段的旧向量与最近消息历史；仅标记 pending 并不足够，这一处已落实。
- 登记、执行、拒绝查询三条工具路径均替换为同一 prepared 正文；Rust 正式保存成功后才建立采用映射。
- 原正式保存成功而索引提交失败时，回执说明正式成功和索引失败，并按预定规则降级到正式目录。
- 评分去除了 app/元 子串真值；临时覆盖检查正式资产快照未变。故障必须有实际触发记录。
- 产品 `memory_source()` 修改只认可已结束的句子及换行边界；前置否定、尾部临时限定的拒绝条件保留。

## 并发与证据记录

- 两条重复链各自使用 AsyncLocalStorage 上下文、独立数据库及集合；组顺序交替。Pi 的 ModelRuntime 和工具 transport 按 deliver 实例建立，锁定 SDK 的 provider 注册属于实例。
- Agent 预算预留使用串行锁，汇总已完成与全部活跃组合。组合结束时将活跃账本迁入已完成计数的操作没有异步间隙；未发现正常完成路径的重复计算或漏计。
- 报告写入串行化，恢复核对完整冻结文件集合及内容。真实小样未发现跨组正式资产或工具回执绑定。
- 并发两轮仍只有 9 种正常情境；共享模型服务和本地资源会影响耗时，不能据此宣称独立业务样本数增加或固定性能收益。

三个正常记忆失败分别是 A 的临时覆盖第一轮、金额单位第二轮，及 B 的修订第一轮。核对 `source-rejection-analysis.json` 所引 7 份 Pi 原生 journal 及其 SHA 后，确认三组均反复修改 `scope`，却继续使用裁去“请记住：”的 `instruction_quote`。24 次工具回执为 `scope_incomplete`；来源边界实际拒绝的是引用起点。该通用错误没有说明应修正原文引用，模型最终回答也将它理解为作用范围字段问题。此为共享工具反馈的改进依据，不足以归因 Mem0 提取优劣。

B 的另一项完整失败来自 `temporary_only` 第一轮：记忆隔离和两条 SQL 均正确，但最终解释声称“1 月之后发生的退款未纳入”，与截至 2 月 4 日的快照及原付款月归属矛盾。该场景没有长期记忆写入，不能归因于 Mem0 提取。

## 故障证据与测量修正

- B 提取失败两轮均触达，并正确告知未保存；后续没有复用失败候选。
- B 索引提交失败一轮触达，正式保存成功后如实说明目录降级并在新对话采用 web；另一轮先被来源校验拒绝，故障未触达。
- 数据库故障在 A 第一轮、B 第二轮分别留下两条 `storage_failure kind=database code=45000`，两组均正确告知未保存，后续不复用失败偏好。A 第二轮先被来源校验拒绝，B 第一轮模型调用失败；两项均未触达数据库故障。
- A 的提取、索引四组合是无故障参照，通过 3/4。真正适用的故障触达与正确处理是 A 1/2、B 4/6，分母含义不同，不直接比较可靠性。

原采集器只匹配数据库错误原文，漏掉脱敏的 SQLSTATE 45000；独立日志核对发现上述两项误报。保留原始 `result.json`、`scoring.json` 和 `scoring-before-log-correction.json`，另生成 `scoring-log-corrected.json`。原、修正评分的每步检查完全相同，仅这两项的故障触达及机器场景结果由 false 纠正为 true。缺失或未触达的组合没有改分。

正式批次结束后，只修正三处证据代码：runner 的日志识别、scorer 的日志核验与独立输出文件、audit 的精确 SHA 复核入口。145 个冻结文件中，其余 142 个保持一致。独立 `measurement-source-review.json` 绑定每个改动的 measured/current SHA、整份结果 SHA 与证据用途；完整 audit 通过。无审查记录、错误结果 SHA、错误文件 SHA、非证据改动和缺文件记录均被拒绝。新增评分自测后共 10 项通过，runner 语法检查通过。审查者未调用付费模型，未重跑失败。
