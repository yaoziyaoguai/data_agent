# 本地角色与对话试用记录

日期：2026-10-10。源码基线：`ba21773228e7a73cc69a655f0e46b40d2ea101f6`，分支 `codex/conversation-experience`。本轮按用户要求实际操作页面、核对结果并讨论来源同步；没有修改产品代码，也没有实现新的同步方案。当前决定及后续安排以 [CURRENT](../CURRENT.md) 为准。

## 结论

权限与纠错协作、聊天修订后执行 SQL、结果预览与下载、个人 Skill 发布公共副本等流程在本轮走通。另有两项已确认的问题未修复：**模型把正确的查询结果总结错；历史结果过期时，错误码在前端契约校验中丢失。** 语义目录和对话展示仍有阅读负担。

本轮使用真实 DeepSeek Flash（关闭思考）的一个三轮对话；Datasight 为本地合成数据平台。三轮指三条用户消息，不代表三次模型 API 调用。没有进行批量准确率评测，也没有据此重新验收整个 MVP。

## 已确认问题

### 1. 查询正确，结果总结不准确

试用请求是读取 `demo_order_detail` 的全部非测试订单明细，保留金额单位“分”，不限制月份或支付状态。第二轮添加订单状态列后执行。

| 核对项 | SQLite 独立参考 | 模型首次总结 | 追问后的总结 |
| --- | ---: | ---: | ---: |
| 明细行数 | 14 | 14 | 14 |
| 去重订单数 | **12** | 13 | **仍为 13** |
| 支付金额大于 0 的行数 | **12** | 11 | 12 |
| 支付金额等于 0 的行数 | **2** | 将支付金额与净额混用，概括为 3 行 | 2 |

`O1001` 与 `O1013` 都有两行，因此 14 行对应 12 个订单。追问后模型漏算了 `O1013` 的重复订单号。其回复同时包含 `O1013` 的两条明细及退款解释，现有证据不支持简单归因于“结果没有传给模型”。本轮没有读取完整模型请求或定位模型内部原因。

SQL、数据库结果和下载文件相符。问题发生在自然语言总结中的计数与口径区分，影响用户对分析结论的信任。建议后续优先让可核对的统计计算支撑数值结论，模型负责解释；具体实现尚未决定，不在本轮新增计算框架或固定 Agent 流程。

本地证据：

- `.local/dogfood-20261010/query-independent-reference.json`
- `.local/dogfood-20261010/download-verification.json`、`orders.csv`
- `.local/dogfood-20261010/query-before-correction.txt`、`query-after-correction.txt`

### 2. 历史结果过期被显示为技术报错

打开已有查询，页面显示“查询完成”，结果区却显示 `invalid_input: AppError`。网络回执为 HTTP 409，错误码是 `result_expired`。

已定位的路径：

1. [平台适配](../../crates/data-agent/src/modules/queries/platform.rs) 保留了 `result_expired` 错误码。
2. [AppError 契约](../../packages/contracts/schema.json) 的 `code` 枚举缺少此值。
3. [Web API 客户端](../../apps/web/src/shared/api.ts) 先解码错误响应；[契约校验器](../../packages/contracts/validate.ts) 因此抛出 `invalid_input: AppError`。
4. [查询组件](../../apps/web/src/features/workbench/QueryCard.tsx) 已有“结果已过期，可以在对话中要求重新查询”的中文提示，但收不到原错误码。

使用捕获的错误响应直接调用项目解码器，复现同一报错；契约枚举检查也确认缺少该值。根因是接口错误契约遗漏。这条历史查询曾执行成功，不能将结果过期提示错误描述为 SQL 执行失败。

证据：`.local/dogfood-20261010/expired-result-response.json`、`history-result-error.png`。本轮仅定位，未修改契约或代码。

## Datasight 增量同步：现状与讨论依据

此节是只读核对和候选方向，**不构成新功能决定或已实现能力声明**。

### 现有底座

- [目录同步用例](../../crates/data-agent/src/use_cases/catalog_import.rs) 按空间、来源命名空间和平台稳定 ID 识别对象，核对分页快照与采集前基线。
- [来源存储](../../crates/data-agent/src/modules/ingestion/store.rs) 已有快照、当前版本及内容指纹；没有变化时跳过重新分析，人工覆盖沿用正式合并规则。
- 只有完整的权威目录才处理缺失对象；部分读取不能据此判断表已删除。
- 新表先创建基础元数据知识。新对象初版且未标为优先分析时，不立即排深度模型预填；基础可见与语义分析完成是不同状态。
- 页面提供手动“同步来源”。本轮搜索生产调用入口未发现自动定时或事件监听接入；没有连接真实 Datasight 验证其接口能力。

### 当前不足

[来源正文构造](../../crates/data-agent/src/modules/ingestion/catalog.rs) 包含整份表 JSON，含负责人、来源版本、字段和节点等信息。[同步用例](../../crates/data-agent/src/use_cases/catalog_import.rs) 使用表级 `changed` 判断，命中后遍历该表及其字段重新分析并排预填。因此仅负责人变化也可能让整表与全部字段进入这一处理路径。这个结论来自静态控制流核对，本轮没有触发同步或执行相关模型预填。

界面尚无清楚的“发现了哪些新表、哪些资料变化、影响哪些语义、哪些需要处理”清单。设计中已有增量预填职责，实际变化处理仍比设计粗。

### 对“缓冲地带”的初步理解

一个表对象应组织表结构、字段、负责人、加工 SQL、调度节点、血缘及相关业务说明。公共文档、指标仍是有独立归属的关联对象，不因为关联到表就被平台同步覆盖。

建议先沿用已有来源快照和任务机制，形成可追溯的过程：**取得平台资料 → 与上次资料比较 → 记录具体变化及影响 → 更新事实、补充必要语义 → 更新检索。**

- 新表先登记基础事实，再补语义；仅改负责人时同步维护归属；SQL、字段含义或类型变化时分析相关内容及其依赖。
- 只处理变化及受影响部分，但不能把“只有一张表变了”等同于“其他引用它的指标或下游永远不受影响”。
- 人工填写保留；新事实与人工值冲突时提示复核。已删除字段、撤权或已知失效资料不能因等待审核而继续被当成有效依据。
- “快速发现”的方式取决于 Datasight 能否提供变更时间、事件或增量目录。暂不假设已有这些接口，也不承诺同步时延。
- 来源快照已在 MySQL 中，不必仅为这一过程先增加数据库、消息系统或微服务。

后续优先讨论新表同步后的可见性与可用范围，再讨论触发方式和变化处理规则；本轮不修改架构基线。
