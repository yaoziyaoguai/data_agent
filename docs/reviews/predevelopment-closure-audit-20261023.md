## 1. 总体判断与审计边界

原十二模块、具名组合用例、React/Rust/Node 进程分工可以保留。本轮未找到必须换数据库、增加服务或重建 Agent 的依据。主要问题在模块交接合同、更新含义、兼容消费方以及文档的现状/目标标识。

沿两条链检查：

1. 空语义库 → 目录/字段/完整生产 SQL → 当前来源与基础知识 → 异步整理 → 索引 → 下次变更或删除。
2. 用户问题 → 任务与条件 → 检索/读取/必要支持 → SQL 与执行 → 结果 → 多轮及检查点恢复。

“设计尚未实现”不单独列为缺陷。以下区分源码已证实的行为、目标合同未闭合、未来需要实际验证的能力。本轮没有取得真实平台行为、大空间性能或真实模型质量证据。

## 2. 需要在相应开发增量前收口的问题

### A1. 输入资料前提已澄清，撤回额外状态体系建议

**用户明确：**上游提供权限范围内完整且含义清楚的表、字段、负责人及当前完整生产SQL资料；无权限资料不提供。生产SQL是已上线的生产逻辑文本，Data Agent同步、保存、比较和解析它，不执行这份生产SQL。

原审计的“SQL超时”指获取SQL文本的接口超时，不是执行SQL超时；这是未经真实平台证实的假设。此前以资料可能分项缺失、权限拒绝混入空值为前提，建议新增取得状态；在用户已明确的输入合同下，不将这些假设继续列为架构问题或开发阻塞，也不新增逐资料不可得状态和最后成功正文展示流程。

[CatalogTable/CatalogPage](../../packages/contracts/schema.json)及[目录导入](../../crates/data-agent/src/use_cases/catalog_import.rs)已有身份、分页和完整目录退休规则。普通同步失败按已有错误处理，未完成同步不推断删除，保留即可。同步何时触发仍属于第5节的独立讨论项。

### A2. “内容没变就复用”需要明确哪些字段算内容

**源码已证实：**[catalog::source_text](../../crates/data-agent/src/modules/ingestion/catalog.rs)把完整 `CatalogTable` JSON 写入来源正文；[save_catalog_table_in_tx](../../crates/data-agent/src/modules/ingestion/store.rs)对这份正文做指纹；变化后[导入用例](../../crates/data-agent/src/use_cases/catalog_import.rs)更新知识并排预填。因此仅 `platform_version` 提高也会改变内容指纹；负责人随平台版本一起改变同样会触发重整，若只改负责人而平台版本未变，则会落入同版异内容冲突。这里需要确认的是适配器的版本语义，不能把所有元数据变动都当成语义变化。这些分支可从代码直接确定，不依赖模型试验。

**建议：**分开规范化业务内容指纹与平台观测/归属元数据。表字段、注释、DDL、完整 SQL 等实际输入改变才推进相应语义修订；负责人和权限变化仍独立生效。平台观测版本继续记录，不能为避免重算而丢掉倒退检测。明确依赖指纹的组成，避免换索引集合时顺带重新分析 SQL。

**用户已明确的原则：**只增减不影响SQL含义的空格、换行等排版，不应触发语义重新整理。建议比较工作由程序完成，不为每次同步额外调用模型判断“是否变化”。

建议按下表固定比较与更新规则；这是工程建议，尚未修改正式Schema或实现：

| 变化 | 比较依据与处理 |
| --- | --- |
| 平台版本号、采集时间变化，资料内容相同 | 更新观测信息，不重新解释资料 |
| 负责人变化 | 更新归属，不触发SQL解析或业务语义重整 |
| SQL仅排版变化 | 按实际方言分词，比较保留种类与值的token序列，忽略不影响解析的空白；规范化相同则复用解释和关系 |
| SQL条件、常量、字段、JOIN、计算、去重或窗口规则变化 | 视为内容变化，重新处理该表生产SQL及受影响的依赖，保留人工值；不全库重做 |
| SQL业务说明注释变化 | 执行逻辑可复用，但说明是语义资料，更新受影响的解释；不能把所有注释直接丢掉。具有执行含义的hint/注释仍计入SQL比较 |
| 字段名称、类型、可空性、表/字段说明等变化 | 按稳定对象身份比较实际属性，处理受影响的对象与依赖；不把整个平台响应的序列化差异当作业务变化 |
| 文档变化 | 比较正文与结构，不套用SQL去空白规则；Markdown缩进、表格、代码块等可能承载含义 |

规范化必须保持字符串、带引号标识符、数值、运算符和token边界；例如`'a b'`与`'ab'`不同。只按方言规则归一SQL关键字大小写，不对所有名称一律转小写。语句改写后的普遍等价性不在本轮范围；未识别为可忽略格式的变化按内容更新，不构建另一套SQL等价证明器。

**原文与成果分开处理的建议：**当前SQL原文仍保存平台最新版，只有排版变化时只更新原文和必要的出处定位，复用规范化输入对应的语义成果；原文片段索引按实际文字与位置变化更新，语义索引不因此全量重建。内容指纹是输入比较摘要，不是模型已经证明两份SQL语义等价。若全文一字未变，且已有成果及其依赖仍有效，则直接复用。

还需补清：`source_preparations`以来源修订和方法版本标识成果时，上游依赖变化但主文档未变，旧成果如何失效、如何重做及拒绝晚到写入。使用已存在的尝试/作业记录即可，不需要建立另一套编排器。

Oracle补充、经本地复核成立的两个分支：

- **旧资料没变，但从未整理。** 旧实现首次导入普通表会跳过预填，F03又把“无变化”直接接到结束。内容未变只能跳过内容更新，不能跳过“准备成果是否缺失/过期”的判断。升级后须幂等补排未整理资料，不能等用户改一次表或勾成常用。
- **正文与出处的复用不同。** 文档插入一段后，旧业务定义也许仍适用，旧offset却已错位。复用文字仍须核对当前出处，做不到就重整单文档。文档原文修订与派生语义修订的推进也须分清；单纯保存整理成果不能让自己的输入原文变成新修订，再导致成果立即失效。

### A3. 原文与整理成果的检索交接（设计已收口，待实现验证）

**审计时的缺口：**[实现设计17.3、17.5、17.6](../architecture/implementation-design.md#17-语义检索与上下文的实施合同2026-10-23)已有完整原文、默认异步整理、定位读取和全片段索引要求，但未经模型整理的原文怎样进入索引、如何与整理陈述区分、如何绑定引用与更新状态尚未写完整。

**反例：**用户刚上传一篇混写多表的文档，整理尚未完成；问题答案在文档后半段。如果只把已整理的陈述加入检索，原文虽已存入 MySQL，Agent 仍可能找不到它。现有[向量片段实现](../../crates/data-agent/src/modules/retrieval/vector.rs)还跳过 DDL/ETL、每对象最多128块；这些是已知迁移差异，不是新发现的架构故障。

**用户同意修正方向并强调正常问答不通读全文。** 已在[实现设计17.6.1](../architecture/implementation-design.md#1761-原文与整理成果的检索交接)固定：原文保存同事务分别登记索引/整理待办；source_excerpt与knowledge_entry共用公共集合并分别回源；明确两类hit及read_source/read_knowledge的定位；保存、准备与索引进度分开；无类型配额、无强制全文，必要支持未知不等于没有例外。只重建索引不重跑语义整理，派生陈述保存不推进原文修订。关联多表的文档不将整篇关联强加给每个片段。

原文索引仍有异步延迟，已保存/按ID可读不等于已可通过问句搜到；索引滞后按既定取舍表达，不新增全库扫描、第二套索引或持续提醒。后台整理全文与聊天检索分开，聊天只交付命中片段及本题所需支持，超长内容按明确位置续读并受实际容量限制；Pi原生压缩继续负责长会话。

模块说明、F03/F04及S04图源已对应修改，7项待实现验收覆盖整理失败下的文末召回、多对象归属、跨段例外、同源去重、旧位置、索引重建及超过128块的长资料。A4个人资产兼容、A6有效层依赖和A7必要支持交付仍各自保留，不能借A3收口宣称这些也已完成。没有运行产品测试或取得真实模型检索效果证据。

### A4. 新工具表遗漏了已有的个人资产消费方

**已核对：**[实现设计17.5](../architecture/implementation-design.md#175-搜索批量读取与内部组合合同)的 v2 表主要描述公共知识 `hits` 和 `EvidenceRef`；而当前[工具分发](../../crates/data-agent/src/use_cases/data_tools.rs)同时提供个人记忆目录、记忆正文/适用范围/原话分页和已选 Skill 目录。现有 `EvidenceRef.path`定义为知识对象条目路径，不能不作说明就拿来代表个人原话。

**反例：**新运行升级为 v2 后，模型想补读一条个人记忆中的例外，只有公共知识引用结构可用；若实现者照新表替换旧工具，可能意外丢掉 `scope`、`source_text` 或个人资产分页。

**建议：**补 v1→v2 调用者与返回字段对照，明确个人资产引用及分页如何延续；Skill 正文继续走 Pi 原生 `read`，Mem0 存储不变。还要覆盖同一长期 Pi 会话从 v1 进入 v2 时的历史工具内容和未完成回执：沿原操作身份接回，不因换合同重做副作用。属于保持现有能力，不是新增资产功能。

### A5. “旧记录保留”没有回答“旧结果还看不看得到”

**源码已证实：**[context_authority](../../crates/data-agent/src/use_cases/context_authority.rs)要求知识及来源修订仍为当前；[query_workflow](../../crates/data-agent/src/use_cases/query_workflow.rs)遇到相应失效会隐藏 SQL、参数、摘要等正文。目标17.3/17.8说保留任务、SQL和终态记录，但沿原有效性检查时，普通语义改版仍可能让引用它的旧查询正文不可见。

**反例：**昨天完成的分析引用一篇文档；今天只是修改文档描述，用户刷新昨天的查询，SQL/摘要被隐藏。数据库记录没删，用户仍无法回看。这与“不持续跟踪、提醒、重算旧分析”并不是同一个决定。

**用户已同意的方向：**区分历史展示、新分析采用和权限撤回。普通语义改版不隐藏已完成分析保存的SQL、条件、结论和报告；不冒称它采用了最新口径，不承诺恢复未保存的旧全文或永久读取平台原始结果。新分析核对当前语义，保留原分析。撤权与结果有效期等访问条件单独处理；不增加变化监听、主动提醒或自动重算。目标接口尚待统一同步，实现尚未修改。

### A6. 统一依赖索引还需区分有效层、必要依据和调查材料

**Oracle提出、本地复核成立：**17.3把 `material_refs`、`structured_evidence`、结构依赖、支持及出处汇入统一索引；17.6又用“全部必需来源”判定可读。与此同时，[M02条目合同](../architecture/knowledge-modules.md#31-条目级语义)保留事实、模型建议、人工覆盖，并另选 `effective_value`。目标未明确这些层与依赖用途怎样对应。

**反例：**旧建议依据文档B，维护者后来依据A明确修订。把所有层的依赖无差别取并集，会让过时的B继续阻断有效人工值；看到人工值就清空依赖，则可能丢掉仍然必要的B。仅仅读过的背景材料C，也不能自动变成结论必需的来源。

**用户已同意方向：**保留同一依赖索引，注明归属条目及内容层、依赖用途和记录是否完整。变更影响查询可以覆盖较宽的潜在依赖；当前采用/来源过滤应使用实际有效层的必要来源。普通关联不等于必要前提，依赖未知不等于已确认空集合。保留人工编辑和遵守已确认来源限制均已决定，无需重新设置逐条审批；具体有效层选择需要成为可测试合同。

**本轮讨论举例与边界：**当前成功率定义依赖文档A的有效请求规则；已被实际替换的旧建议曾依赖B；C仅作调查背景。A的相关规则变化需要重新核对当前定义，B的变化只影响仍依赖B的内容，C普通改版不因曾被阅读而使当前定义失效。人工保存/编辑不是清空依赖的依据，未被替换的内容仍保留真实来源。这里区分的是业务语义与更新影响；实际交付记录和访问权限另按原规则保留，不能仅凭模型声称“没用过”删除来源追踪。方向已确认、目标接口仍待细化，不新增审批、每轮依赖判断模型或图服务。

### A7. “必要支持已交付”不能仅代表支持ID已列出

**Oracle提出、本地复核成立：**17.2的 `supports` 是角色及引用，17.5的 `support_state=delivered` 又表示支持交齐，17.6按最多50个支持引用分页。文字未排除“引用交齐但必要内容没交付”的实现。

**反例：**回执给出成功率定义和一条指向文档末尾排除条件的引用，标为 `delivered`；模型据此省掉补读，排除条件从未进入上下文。

**建议：**明确哪些实际交付的内容满足了必要支持。条件已完整写入陈述，或必要片段已经交付，才能作相应的完成声明；只有ID不够。分页结束只代表已记录支持遍历结束，未整理/依赖未知仍如实表达；不借此声称已经找齐世界上所有例外。状态辅助Pi判断与补读，不新增强制通读全文或人工确认流程。

**具体修正建议，待确认：**

- 必要的短条件/例外优先随定义返回，并保留出处；已由正文完整承载的支持不再重复交整段原文。整理时保存支持与承载内容的对应关系，不在每次回执时新增模型判断或按关键词猜语义等价。
- delivered只声明本次回执已实际包含所记录必要内容；只有引用或必要正文被裁剪时为partial，并给出未交付项及可读取位置。未知提取完整性仍为unknown，不因引用列表为空或分页结束变成delivered。
- 状态在最终工具回执裁剪后计算；桥接端若再次删减必要内容，必须同步降级并保留补读位置。不要按数据库里“有正文”或模型“曾看过”直接声明当前回执交齐，也不新增跨会话支持交付账本。
- 限额仍按原工具/上下文容量，已知缺口由Pi按本题需要定点补读；不能把partial/unknown机械变成禁止回答、强制全文或递归穷尽所有关系。交付不等于模型理解正确，也不保证之后压缩仍保留全部细节。

**待实现验收：**只给公式及例外引用不能标delivered；公式与必要例外实际返回才可标delivered；裁剪例外后状态必须降级且可定点补读；只有引文目录翻页结束仍不能冒称正文交付；未整理的原文unknown不触发强制全文；相同内容已在定义中交付时不强制重复读取。当前没有修改产品接口或运行这些验收。

## 3. 开发者应补齐的工程细节

| 项目 | 具体缺口与处理建议 | 需要的验收 |
| --- | --- | --- |
| 完整大 SQL 的接入容量 | 当前 CatalogNode SQL/DDL最多40000字符、列最多200、目录最多100页，平台页最多8,000,000字节。目标说完整保存，尚缺这些边界的迁移和续读合同。保留有界传输；不能只把模型窗口调大或截断后称成功 | 大 SQL 尾部CTE/过滤完整；宽表字段未静默丢失；超限有明确继续或失败语义 |
| 准备成果复用 | 写清来源内容、依赖版本、解析/整理方法版本各自如何影响复用；输入不变不重做，依赖改变不能误复用旧成果 | 主文档不变、引用定义改变后正确重整；索引重建不再跑模型整理 |
| 来源和位置 | source/knowledge/index身份分开，Unicode位置与原字节/行号引用在owner边界转换；固定修订后才解释offset | 中英文、补充平面字符、换行和改版续读不串位；不拿新正文解释旧位置 |
