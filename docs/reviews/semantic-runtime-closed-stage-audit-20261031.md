## 2. 优先处理的问题

### R01｜P1｜普通自然回答缺少提交前的来源有效性重核【已运行复现】

**触发与影响：**读取有效知识后，该知识被维护者停用，再提交没有 `answer_parts` 和 `answer_sdk_tool_call_id` 的普通 final，仍返回 200，写入 `committed`，任务变成 `answered`，消息变成 `consumed`。停用前后两组对照均有正式输出。

**根因与位置：**`use_cases/finish_run.rs:62–91,130–149` 对 parts/答案工具引用有来源检查，普通分支 `161–181` 只核持久正文并提交。`apps/api/src/routes.rs:253–263`、`runtime/checkpoints.rs:11–20`、`runtime/store.rs:353–365,435–465` 和模型调用结算没有补上该责任。

**证据：**`natural-answer-authority-result.json`。这是正式接口“读取→停用→自然 final”的复现，未运行真实模型暂停/返回实验；provider 完成仅结算用量、不会补校验的路径另由源码确认。

**修复方向：**在既有最终提交事务内复用当前 authority 校验，覆盖自然 final，拒绝发生在正文提交、任务推进和消息消费之前。不增加实时监听或另一套权限机制。发生频率没有测量；这是已明确要求的停用/撤权边界，不是假设新的并发保护需求。

### R02｜P1｜答案可以先定稿，再进入无法合法提交的长度状态【已运行复现】

**触发与影响：**7900 字正文定稿后可以组合提交；7998 字正文也被允许定稿，但仅加其标题就已达 8008 字，随后加一个字的末项答案，最终提交返回 `400 invalid_input`，冻结项仍保留，输出未提交。缩短末项不能解决前项自身加标题已超限的问题。

**根因与位置：**`task_answers.rs:248–262` 只核单篇正文不超过 8000；`274–305,362–366` 最终组合才把标题、分隔和多篇正文纳入同一个 8000 字上限。冻结后又必须保留原文、禁止同任务重新冻结，两处合同不一致。

**证据：**`frozen-answer-length-result.json`，两组真实接口对照。

**修复方向：**定稿准入和最终组合使用一致的长度口径，在冻结前计入已冻结内容及格式开销，让 Pi 在定稿前获知剩余空间。不要静默裁掉已冻结正文、重写前项或增加汇总模型。是否扩大总上限另属产品选择，不作为默认修补。

### R03｜P1｜同原文修订的依赖变化重整，会撞旧调用和应用操作身份【静态调用链确认】

**触发与影响：**准备已完成，依赖内容实际变化，但该来源原文修订不变。正常扇出重开后，首批会再次使用旧模型调用 ID，在发送前插入主键冲突，准备失败。即使只修该处，新成果的应用还可能撞旧操作指纹。

**根因与位置：**`source_fanout.rs:121` 重开依赖者；`ingestion/preparation/store.rs:188` 将 `batch_sequence` 清零；`ingestion/preparation/mod.rs:27–44` 的调用 ID 只有 source/revision/method/sequence。`source_preparation.rs:285` 预留调用，经 `runtime/model_calls/store.rs:63` 直接插入既有主键。应用 operation 在 `source_preparation.rs:378–384` 只有 source/revision/method/batch_start，新内容再受 `knowledge/store.rs:32–36` 的幂等冲突约束。

**边界：**旧 unknown 没有被重开，未发现重复收费；当前首先发生的是不能完成新一轮整理。这是前置整理模块在当前完整链路中暴露的继承问题，不据此推断由 08 新引入。

**修复方向：**区分原批恢复与终态后新批，优先复用已有单调批次身份，应用 operation 与同一批身份一致。不新增第二套 epoch。补 `ready→依赖变化→同 revision 重开`；现有尚未成功应用时的重开测试不能代替它。

### R04｜P1｜archive 模式下，同修订文档整理覆盖既有完整快照【静态调用链确认】

**触发与影响：**已有 D/v1 完整归档，兼容升级仍使用 archive；后台整理在不改变原文修订的情况下更新陈述/关系。旧 `knowledge_versions(D,1)` 被删除，然后以更新后的完整对象重写。

**根因与位置：**`knowledge/preparation/store.rs:205–232` 同版文档分支删除归档；`knowledge/store.rs:185–227` 的 `persist` 再插入完整对象。原文字节不一定改变，但 suggestion、statements、relations 可以在原归档版本号下变化。

**合同：**`compatible-upgrade.md:19` 和实现设计 17.8 要求既有 `knowledge_versions` 原样保留。现有“文档升到 v3 后 v1 保持”用例没有覆盖同版后台整理。

**修复方向：**同修订派生更新可以改 current/派生登记，不能删除或替换已存在的 legacy 归档。沿用“原文修订不因自动整理增加”的决定，明确当前派生视图与精确历史档案的读取职责；不扩建永久全文历史系统。

### R05｜P1｜同版文档重整清空知识索引的冻结维护配置【静态调用链确认】

**触发与影响：**同对象版本的知识索引首次已经冻结 profile/trial A；文档整理删掉并重建待办后，后续新文本索引会采用当前环境的 trial B。若当前环境已无维护配置，则原本可恢复的待办因缺冻结配置而无法领取。

**根因与位置：**`knowledge/preparation/store.rs:222` 删除同版待办，`knowledge/store.rs:204` 新建默认行，清掉 `embedding_profile`、尝试次数和租约代次。`knowledge_embeddings.rs:253–258` 的 `Binding::Index` 只从新行或环境取 profile；`knowledge/store.rs:1653` 的领取条件依赖冻结配置。

**合同与限定：**实现设计 `:259` 要求冻结该对象版本首次维护额度。旧付费调用账本仍在，`provider_calls/store.rs:221–242` 会接回 settled，拒绝 issued/unknown；**未证实同参数重复收费，不能把本问题描述成无条件重复调用模型。** 多消费者下的租约 ABA 尚无运行前提证据，不列入必修。

**修复方向：**保留同版待办的原身份和冻结配置，只更新新内容确实需要推进的状态，复用现有账本；不新建恢复框架。

### R06｜P1｜额外 Mem0 命中仍能在小容量时静默消失【已运行复现】

**触发与影响：**目录命中 B，Mem0 额外召回 A；用实际 `toolResponseCapacity` 对合成长会话分配回执额度。额度为 1200 字节时 A/B 都保留；1000 字节时成功回执只有 B，序列化 814 字节，`next_asset_after=null`，没有 A 的身份或补读位置，也没有触发容量错误/压缩信号。

**根因与位置：**`evidence_delivery.rs:241–264` 将 A 放在目录后；`299–320` 缩小 `kept_assets` 时先删 A，但游标只记目录。正文裁剪修复没有覆盖最小身份集合也放不下的分支。`capacity.ts:130–136` 没有约 18KB 的最小额度保证。

**证据：**`memory-capacity-result.json`，真实 Rust/隔离 MySQL、实际宿主容量分配、局部 Mem0 协议替身；首次冻结回执与返回值一致。没有把该实验当真实 Mem0 或真实模型质量验证。

**修复方向：**保留额外项的最小身份/版本/补读位置，容纳不下时沿现有容量错误让 Pi 处理。目录项仍使用原目录游标；不加 Mem0 游标服务。

### R07｜P1｜跨页去重历史不断累计，正常深翻页最终无法继续【静态调用链确认】

**触发与影响：**同查询持续续页，每个已结束候选窗口都被加入 history；累计记录最终撞上 1000 条或 65KiB 游标上限。旧游标重试仍会失败，扩大本页回执预算或压缩 Pi 历史不能移除这个固定失败点。历史还包括退休/失效候选，不必成功交付 1000 条答案才触发。

**根因与位置：**`knowledge.rs:1782–1813` 的 snapshot、`:1836` 的 history 校验、`:1946–1956` 的 `next_history`，以及 `:2409–2415,2910–2923` 的继承。单次候选上限被变成了整个查询分页历史的额外上限。

**修复方向：**调整当前无状态游标内去重信息的生命周期，利用已消费位置和窗口边界，只保留仍可能由其他通道重返的必要身份。不能直接移除上限改成无限增长，也不新增服务端检索会话。完整运行反例需保证超过累计界限时仍有后页；恰好最后一页可能提前结束而绕过该分支。

### R10｜P2｜旧查询通知运行内 route 到当前版本后，合法旧结果答案被 Node 拦住【静态调用链确认】

现有晚到正控在测试 helper 中直接 revise，却未同步传给 deliver 的 Node `active_task_ref`，因此没有证明真实工具 route 后的组合路径。需补实际 Node 工具调用后的反例，不能据此声称所有首次晚到通知都失败。

### R11｜P2｜长支持先占满空间，短而完整的例外被延后【静态分支确认】

`evidence_delivery.rs:351–392,694–736` 按命中顺序分配支持。首条长支持放不下时立即填入尽可能长的前缀，后面本可完整放入的短条件/例外失去空间。这违背实现设计 `:773,814` 的完整短条件优先。

### R12｜P2｜未执行 SQL 后备，其截词限制仍污染正常混合检索覆盖状态【静态调用链确认】

### R13｜P2｜覆盖检查没来得及完成，被说成索引已滞后【静态调用链确认】

### R14｜P2｜部分召回分片失败，故障原因没有进入 v2 回执【静态调用链确认】

一个分片失败、另一个成功时，`vector.rs:1118–1138` 保留失败和 bounded；`data_tools.rs:1299–1323` 只要某片成功就将通道标 available，只有整路 unavailable 才加入故障原因。当前 `quota_limited` 和 `refresh_progress` 也没有把该故障变成 v2 的相应 reason。

## 4. 需要讨论或统一的合同

### D1：跨来源多任务的纯状态确认

任务都在等待执行确认或后台结果时，只回复“两条查询已保存/已提交”是否仍须逐任务定稿？`task_answers.rs:128–133` 把这些等待任务纳入自然回答范围检查，但 `finish_run.rs:221–224` 实际会保留其等待状态，不把它们结清。修复包要求所有无 parts 提交核范围，与原 07 保留自然保存确认的要求有张力。

建议允许根据宿主持久操作/等待状态进行简短控制确认，不把未完成分析标 answered；真正分析答案仍按各任务来源交付。不能通过识别正文中的“已保存”来决定，也不能删掉整个多任务范围检查。

### D2：待澄清的问题怎样算已向用户交付

自然 final 路径排除 `waiting_clarification`，parts 路径却要求所有未取消任务都有引用。A 待澄清、B 已答时，需要统一“任务卡已可靠显示 A 的问题是否足够”，还是必须在最终正文重复 A 的问题。
