## 已确认的行为问题

### 1. P1：依据正文与支持补读重新占住会话锁，支持脱离搜索期限

**触发与影响。** 搜索主链已在锁外，但命中附有条件/例外时，06 又在持有 conversation/run/tool 行锁的事务中读支持目录及正文。普通慢查询即可阻塞会话续租；支持读取也未沿用本次搜索的绝对截止时间。批量 `read_knowledge` 和 `read_source` 同样需要核对正文准备边界。

**根因。** `use_cases/data_tools.rs` 把最终回执装配和正文 I/O 放进了同一个提交事务，违背既定“三段式短事务”合同。属于工程实现错误，不是 MySQL 本身不适合，也不是 Pi 应负责数据库锁。

**证据。** 真实 API 登记/执行、隔离 MySQL；代理仅暂挂支持 SQL，未替换响应。修复前独立连接取得 conversation 锁返回 `1205`，搜索/知识读取均复现；放行后真实支持照常交付。纠正前的局部修改后，三类读取锁探测分别约 79/56/57ms，支持仍挂起时 10.093 秒返回主命中、partial 与原续读位置；来源停用拒绝交付，原操作仍重放第一次 partial。

**建议。** 沿现有组合入口释放会话锁后准备正文，最终另开短事务重核运行、任务、来源、权限及实际交付依赖后保存。搜索支持沿同一个期限；不能给普通读取擅加十秒规则，不增加协调框架。

**当前状态。** 纠正前已修改并有局部 GREEN；当前树后续还有未验证改动，未通过整体验收。证据：`.local/checks/evidence-support-lease-{red,final-green}.log`，以及审计目录中的后续 coverage 反例。

### 2. P1：最终裁剪会丢掉 Mem0 额外召回的个人记忆

**触发与影响。** 当前目录页含 B，Mem0 为问题额外召回有效的 A。只要公共支持数量或回执容量触发裁剪，额外 A 就可能消失。模型失去相关线索，而资产目录游标也不表示这条额外命中的续读位置。

**根因。** `data_tools.rs` 先合并 Mem0 命中与目录结果；`evidence_delivery.rs::search_reply` 的裁剪分支却只按 `delivery.assets["order"]` 重建资产，错误地假定目录顺序覆盖全部记忆。后续填充也只处理这份目录列表。

**证据。** 正式工具、真实存储及实际 Pi/provider 输入：前页 A+B、26 个支持、11,628B；裁剪后只剩 B、46 个支持、18,101B。两页先与 Rust 持久回执逐字段比对，再由 A/B 集合断言取得 RED，0 官方模型请求。证据：审计目录 `memory-clipping-red.{log,json}`。

**证据限度。** 实际 Pi 容量只允许交付 46 个支持，后面的“恰好 50”断言没有执行。已经证明额外记忆被目录重建逻辑丢失，不能冒称已独立证明“容量充足容纳 A+B+50 支持”的数量场景。

**建议。** 目录项与额外 Mem0 项共同进入现有容量分配，按身份/版本去重；只有目录项推进 `asset_after`。额外项放不下全文时保留现有身份与补读位置，不新建记忆游标服务或检索会话。

**当前状态。** 产品未修改，仅准备并运行了反例。

### 3. P2：检索覆盖回执遗漏 SQL 后备超时及精确匹配步骤

**触发与影响。** 一个 SQL 候选 owner 已完成、另一 owner 等到搜索期限；最终仍有合法主命中，但回执只报 `bounded`，丢失实际 `deadline` 原因。v2 `channels` 也没有正式合同列出的 `exact` 状态。Agent 难以区分未检索完、通道故障与已完成查询。

**根因。** `data_tools.rs` 主要从 Milvus 的 lexical/dense cursor 反推全链覆盖状态，遗漏 SQL、元信息及正文阶段的共同期限事实。`exact` 实际是 `rank_common` 对已召回、已核验候选的 ID/名称优先步骤，并非第三个物理召回通道。

**证据。** 正式 API/MySQL 反例明确声明零支持，排除支持超时干扰；返回合法命中、`state=bounded`、`reasons=[]`，预期包含 `deadline`。另一反例确认通道数组只含 bm25/dense。证据：审计目录 `sql-coverage-{red,known-supports-red}.log`。

**建议。** 传递并消费现有推进器的实际期限事实，报告精确匹配步骤是否实际完成。资产目录不声称运行了公共精确匹配；成功空候选、步骤前到期与恢复窗口分别核对。不能为输出 exact 增加第三张 RRF 票，也不能固定填 available 或声称全库精确查找已穷尽。

**当前状态。** 纠正前已经修改 `knowledge.rs`/`data_tools.rs` 并准备对应断言；尚未重建或 GREEN。停止继续修复后不完成该修改的验收。

### 4. P1：已有冻结答案时，正常结束可以遗漏第三个任务

**触发与影响。** 同消息涉及 A/B/C，A 已定稿，B 作为最终自然回答，C 仍有效。原接口允许提交 A+B 并消费整条消息，C 被静默漏掉。

**根因。** `task_answers::compose_in_tx` 的“全部未取消任务必须有交付引用”检查只在 `final_text=None` 分支运行；正常 final 绕过了同一个业务不变量。

**证据。** 正式 HTTP/MySQL 反例预期 409、实际 200。纠正前将原检查应用于正常 final 后，原 20 项加两项覆盖反例/正控共 22 项通过；另有 A 冻结、B 取消、C 恢复自然回答及浏览器两次刷新证据。

**建议。** 复用已有覆盖检查，保留正式取消例外及逐部分版本/来源核验；不新增答案账本、工具或模型汇总调用。

**当前状态。** 纠正前已修改并局部 GREEN。不能据此宣称所有多任务提交形态已覆盖，下一项仍然存在。

### 5. P1：没有任何冻结项时，跨来源多任务仍会被最后一个答案全部结清

**触发与影响。** A、B 使用不同的明确来源范围；普通 route 从 A 切到 B，不定稿 A；最后只有 B 的正文。系统成功提交 B，并将 A、B 都标成 answered。

**根因。** `deliver.ts` 仅在已有冻结项时发送 `answer_parts`；`finish_run.rs` 的无 parts 分支接受自然 final；随后 `runtime::delivery_task_refs_in_tx` 收集成功任务更新的引用，把这些任务都推进为已回答。进入严格组合校验的前提本身存在缺口。

**证据。** 这项最初由独立本地审查发现，Oracle 标为需核实；用户纠正后只运行已准备反例，未修改产品。正式接口实际 200：消息 pending→consumed；只有 B 正文被 committed；A/B 均 investigating→answered；没有 frozen part，0 模型调用。证据：审计目录 `task-unfrozen-{audit.log,red.json}`。

**建议。** 最终业务提交入口核对需要分别交付的任务；无 parts 不能绕过跨来源/未知范围的分别交付要求。保留 v1 兼容、单任务、明确同范围的自然综合回答；不把普通 route 改为自动定稿，不从调查文字猜测任务已完成。

**当前状态。** 产品未修改。新增脚本在该 RED 处停止；未知范围及同范围正控尚未运行，不能把它们写为已证明。

### 6. P2：历史报告读取失败时隐藏错误和重试；提示还会先于正文出现

**触发与影响。** 用户打开旧条件的报告，GET 失败。页面原来会因 `changed=true` 隐藏加载状态、错误及重试按钮，只剩“以下为已存内容”，实际没有正文。

**根因。** `AnalysisReport.tsx` 将“条件是否变化”和“本次读取是否成功”混成一个展示门控。历史展示合同已更新，旧 UI 条件没有同步。

**证据。** 真实工作台浏览器 RED→GREEN，成功响应来自真实 API；原金额/205点、窄屏、迟到响应、结果有效期、历史内容和用户隔离等共七项通过。503 注入的响应缺少完整 AppError 字段，实际触发了接收边界错误；它证明“读取失败应显示错误/重试”，不能单凭此声称所有标准服务错误都已分别验证。

**建议。** 读取状态独立显示；只有正文确实可显示时才说“以下为已存内容”。不回退到未经本次权限核验的缓存，不自动重跑查询。

**当前状态。** 纠正前已删除错误/重试显示的 `!changed` 条件，并局部通过。无正文仍显示“以下为已存内容”的文案问题尚未修改。
