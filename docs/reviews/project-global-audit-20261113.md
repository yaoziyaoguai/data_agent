## DA-001：已知指标与匿名边界被混成新度量

原题：

> 查2026年1月整月支付客户数，保留未知客户边界。请先给出SQL草稿，等待我明确要求执行；此时不要提交查询。

实际保存的草稿先计算 `COUNT(DISTINCT customer_id)`，另列匿名订单数与行数，第四列却计算“已知客户去重数＋存在匿名订单时加 1”，命名为 `paying_customers_with_unknown_boundary`。其说明明确把该单位放入总数；用户没有确认这个新指标。

该草稿自己的 `semantic_resolution.interpretation` 写明：匿名客户不并入已知客户、不互相合并，仅单列订单数与行数。这与第四列表达式不一致。平台语法通过不能消除这个业务偏差。

真实 `read_knowledge` 回执中包含完整指标定义和文档字段说明，分别为 434、1150 字符，`content_state=complete`、`source_context_ready=true`。定义给出月内 `COUNT(DISTINCT customer_id)`；文档明确 NULL 表示匿名购买，不能补成统一客户参与 UV。`supports_complete=null` 不意味着这两段正文没交付，也不能冒称支持材料全部齐全。

当前 `apps/agent/tools/data-tools.ts::formatResult` 对 v2 的 `read_knowledge` 直接序列化 `receipt.data`，未在该分支再次裁掉正文。原 harness 记录了 Rust 工具回执与 HTTP 时序，未保存最终模型请求正文。因此可确认模型产生了与已读定义及自己决策不一致的 SQL；**当前没有证据把根因归为 MySQL、Milvus、Mem0、Pi 压缩或模型上下文窗口过小，也不能排除未经记录的末端交付差异。**

独立执行的原结果为 `[5,1,1,6]`，完整四列形状的 `expected_rows=null`。评测器不认识第四列只是其中一项证据；真正的业务依据是原题、指标定义和 SQL 表达式。不能说四列数值都算错，不能通过改列名、删变体、人工改 SQL 或改预期把原失败变成通过。

一般性修法：正式指标沿已确认定义，未知实体/缺失值/覆盖缺口保留独立诊断含义，不擅自折成新的总量、上下界。明确口径直接处理，只有真实的新指标选择才进入现有澄清机制。不新增 SQL 语义等价引擎、额外评分模型或 NULL 特判。

本地证据：`.local/checks/query-submission-implementation-20261110/real-representative.json`、`real-representative-diagnosis.json`；判分入口 `scripts/evaluate_business_sql.py::{customer_roles,customer_expectation,customer_variations}`，既有测试 `tests/mvp/check-business-evaluator.mjs`。

## DA-004：报告引用脱离事件分页后失去位置

调用链已核：

1. `read_conversation::read_page` 分页读取事件，但读取当前会话的任务集合。
2. `analysis::read_tasks_in_tx` 从报告 owner 取得 `report_ref`，不依赖报告保存事件是否在当前页。
3. `conversations::event_page_in_tx` 每页最多 1000 条。
4. `conversationItems` 只从已加载事件找 `analysis_report_saved`，找不到就把报告序号设为 `0`。

使用现有 Schema 校验两份合成 Snapshot：最新页事件为 1001–2000，任务含合法报告引用；早期页含第 25 条报告保存事件。当前投影在补页前为 `0`，补页后为 `25`，报告数量始终 1。这是正常分页路径，非臆造的并发异常。

复现脚本和观测位于 `.local/audits/project-global-20261112/confirm-report-anchor.mjs`、`report-anchor-observation.json`。这次运行证明投影缺陷，不证明浏览器视觉已验收。

建议用现有 `conversation_events` 的首次保存序号，在会话读取用例里通过 conversations owner 的窄查询组合给任务展示投影；前端优先使用稳定锚点。追加确认：`analysis_reports.rs` 页面保存和 `data_tools.rs` 的 `save_analysis_report` 都发出同类保存事件。无需新时间线系统，不应拉取完整历史或改报告内容/版本来解决布局。缺历史事件的旧记录保持明确的兼容行为，不凭空编造锚点。具体接口与兼容验收见执行包。
