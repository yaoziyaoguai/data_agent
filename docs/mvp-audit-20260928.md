# Data Agent MVP 独立审计

原审计日期：2026-09-28；公开改写：2026-10-03。保留历史审计的通用技术结论和公开来源，业务例子全部改用虚构零售样例。原咨询输入、原始回答、日志与会话信息不属于公开仓库，本次没有重跑 Oracle。后续已确认决定以当前记录和实施基线为准。

本文件是专题审计记录；[CURRENT.md](CURRENT.md) 继续作为唯一当前项目记录。审计建议需与已有决定、真实接口和样本验证结合，不自动成为用户已经确认的要求。

## 结论

**当前架构方向成立。MVP 接下来需要明确：每次查询怎么算、缺什么就不能直接算、执行中断后怎么办，以及返回的数据能支持什么结论。**

Oracle 的八项意见大多是在补充已有模块的具体规则。此前比较明显的不足是：提交结果未知时的恢复、结果分页或截断、业务数据到齐依据、共享修改的生效与冲突，以及模型和历史结果的访问边界。已有的组合检索、语义版本、人工修改保护和平台权限方向继续保留。

对主流方案的比较也支持这一判断：dbt/MetricFlow、Cube 将实体、关联和聚合约束用于查询；Genie 等把指标与过滤规则落到表达式；执行 API 明确区分查询状态和结果交付。我们已有相应的语义内容与模块，下一步应让这些内容真正约束计算和解释。

## 八项意见：本地核验与最小补充

以下优先级沿用审计含义：P0 是相关能力投入真实试用前应具备的基础；P1 是首版应有的最小纠错体验。它们不要求现在一次实现全部系统。

### 1. P0：同一份计算规则贯穿计划、SQL 和解释

- **现有覆盖：**[六类知识](semantic-retrieval-design.md) 已有粒度、时间、过滤、指标、关系；[模块输出](semantic-retrieval-design.md) 也包含整理后的需求。问题是尚未规定程序需要哪些具体字段来检查计算。
- **失败例子：**使用当前客户地区解释历史地区分布；或者将每日去重客户数相加作为月支付客户数。
- **最小补充建议：**一次问题确定统计对象与去重键、输入/结果粒度、时间字段/时区/边界、维度取值时点、过滤、关联与窗口顺序；比率再补分子分母及零分母处理。只要求本题需要的项目。绑定语义标识、版本和计算表达式，SQL 与解释都核对这一份规则。
- **如何验证：**同一个设备跨日出现、维表记录改变、关联发生重复时，计划、SQL、参考数值和解释仍一致。这属于既有模块的细化。

### 2. P0：明确本题必须找到哪些依据

- **现有覆盖：**[补齐依据](semantic-retrieval-design.md) 已提出关系扩展、规则补齐和缺口处理；没有把“找到表”当成足够条件。
- **失败例子：**找到退款金额却遗漏订单粒度、退款率分母和测试订单排除范围；必要的关联另一端因向量排名较低而未进入上下文。
- **最小补充建议：**根据本次计算列出必需对象和规则，通过明确的对象引用先补齐已知依赖，再搜索缺项。记录没有资料、权限不足、未同步和预算不足等原因；对用户只显示其有权知道的内容。不能把“没有权限”伪装成“业务不存在”。
- **如何验证：**E04、E14、E15 和跨表问题逐项检查依据是否齐全。现有“一轮补查”只是候选预算，不是正确性保证；多层明确依赖也不应被误解为只能展开一次。达到预算仍缺关键项时保持缺口状态。

### 3. P0：修订后的规则必须真正生效

- **现有覆盖：**[修改与版本规则](semantic-retrieval-design.md) 已有事务登记任务、回源、版本固定和来源变化复核；[原型保存](../prototype/app.js) 仍是本机草稿。
- **失败例子：**页面说明更新，SQL 仍用旧计算规则；两人从同一旧版本编辑，后保存者覆盖前人的修正；一个共享指标变化却没有提示其他表受影响。
- **最小补充建议：**区分本轮查询条件、编辑草稿和当前有效定义；保存时核对编辑起点版本；显示共享影响与依据失效。MVP 可以采用“有权维护者保存后生效”，不必增加专门审批系统，这一交互仍待确认。
- **如何验证：**改计算规则后，后续计划和 SQL 采用新规则；纯文字说明修改只需影响相应解释，不要求 SQL 无意义地变化。旧会话明确提示规则更新，旧编辑和晚到任务不能回退当前版本。

### 4. P0：权限覆盖模型输入、执行和历史结果

- **现有覆盖：**[权限和故障](semantic-retrieval-design.md) 已要求检索、回源和查询遵守平台授权；具体身份与行列权限接口未核实。
- **待核实的部分：**能查询的数据是否允许送到所选 DeepSeek/向量化服务；维护者可见的样例能否被普通使用者检索；撤权后历史结果、日志和会话如何处理。当前部署方式未知，不能判断已有平台缺能力或已经解决。
- **最小补充建议：**明确各类内容可发送到哪些服务；平台强制执行数据权限，Agent 管住模型上下文和自身保存内容的访问。历史记录与结果读取按有效权限检查，结果单元格中的文字也只当数据。跨用户结果共享缓存暂不增加。
- **如何验证：**两个不同权限的身份，外加撤权场景，检查模型请求、查询身份和结果读取出口。只验证执行失败不足以证明此前没有泄露信息。

### 5. P0：提交 SQL 后失联，不能直接再提交一次

- **现有覆盖：**[后台 Worker](CURRENT.md) 已有持久任务和有限重试方向，执行接口与任务恢复尚待细化。
- **失败例子：**平台已收到 SQL，但回复丢失；Agent 重试造成重复扫描。用户点击取消，页面显示已取消，实际查询还在跑。
- **最小补充建议：**提交前保存任务、SQL、身份和请求标识；拿到平台查询标识后持续跟踪。回执丢失时先查证，无法查证则显示“执行状态未知”，不盲目重提。取消请求与已取消分开，按平台真实终态处理成功和取消的先后；Worker 恢复不得覆盖更新的状态。
- **阶段边界：**查询成功后单独做解释；解释失败保留已取得结果，重试解释即可。扫描、耗时、并发和重试需要预算，具体值按平台能力与样本确定。
- **如何验证：**回执丢失、重复点击、进程重启、取消与成功同时发生。核对真实提交次数；MySQL 任务幂等本身不能证明平台只执行了一次。

### 6. P0：结果拿全、业务数据到齐、数值为零要分开

- **现有覆盖：**[MVP 基本分析](CURRENT.md) 已包含取数、汇总和趋势；结果完整性与到齐依据此前没有具体规则。这是比较明显的补充项。
- **失败例子：**只获取第一页就汇总全月；昨日分区尚未完成，就解释为业务下跌。
- **最小补充建议：**结果携带查询标识、字段类型与单位、取回范围、分页/截断状态、查询时间，以及平台能提供的数据版本和到齐依据。到齐情况没有可靠证据时标为未知；最大事件时间不能单独证明到齐。
- **计算边界：**汇总在完整的所选范围上计算，展示可以只显示前几行。模型不以预览行推断总体；数值由 SQL 或确定性程序算出。区分空结果、NULL、0、零分母和权限失败，整数标识与精确小数不能在传输时丢精度。
- **如何验证：**缺一页、迟到分区、空值、零分母和大整数。完整期间结论必须有对应依据。记录口径版本不保证旧数据值可重现；重放能力取决于数仓快照或结果保留方式，不为此默认复制全量结果到 MySQL。

### 7. P0：SQL 要经过不同层次的检查

- **现有覆盖：**[生成语义](semantic-retrieval-design.md) 已明确目标方言、调度变量和解析失败的问题，兼容性本来就需要验证。
- **容易误判的地方：**Rust 解析器通过只代表能识别某种语法；不证明对象存在、查询平台支持该函数、查询只读或统计正确。MySQL 是 Agent 存储选型，实际数仓执行方言需另核实。
- **最小补充建议：**分别检查模板和语法、表字段函数、只读允许范围及权限、平台编译能力、计算规则。优先复用平台能提供的检查。自动修复不能通过删过滤、改时间和换关联掩盖错误，修复后仍核对本次计算规则。
- **如何验证：**真实 SQL 子集覆盖 map、窗口、透传、调度变量与不支持表达式；同时保留“能执行但算错”的反例。本轮没有安装解析器或实际解析这些生产文件。

### 8. P0 验证、P1 纠错：用数值反例验收，并能定位反馈

- **现有覆盖：**[20 个案例及验证方法](semantic-retrieval-design.md) 已区分知识是否找全、口径和结果是否正确，也保留独立验收问题；目前全都待执行。
- **最小补充建议：**每道计算题补必需依据、计划条件、参考 SQL、参考数值及允许的解释。知识不全的题，以正确澄清或指出缺口为预期。分别记录答对、覆盖范围、错误拒答和关键错误；不能通过全部拒答得到好成绩。
- **简单反例：**同一客户跨日支付时，月客户数不能累加每日去重数。零售样例另用一名客户的多个标签演示关联放大：直接 JOIN 后汇总金额会重复，应按计算目的筛选客户集合。
- **反馈建议：**提问页显示本次条件与依据，允许指出找错对象、口径不对、数值异常或解释有误，关联到对应任务和版本。纠正应进入待处理记录；用户点赞或 SQL 执行成功不自动成为已验证案例。
- **如何验证：**正确方案通过、已知错误方案失败；修正相关规则后重跑对应案例。无需立即搭建独立评测平台。

## 哪些建议要收窄

1. **审批和发布：**需要有效版本和编辑权限；单独审批流程不是现阶段必需。上面的“保存后生效”是供讨论的轻量方案。
2. **检索补查：**已有设计已经要求缺关键依据时停止或澄清，Oracle 并未发现当前实现会错误放行，因为真实检索还未实现。应细化完成条件，再通过样本调整次数。
3. **语义修改：**展示说明、计算规则和实际加工事实分别处理。改文字不一定应改 SQL；改正式算法则必须同步影响后续计算。
4. **结果快照：**先明确平台已有能力。没有数据快照时说明复现限制，不默认新建全量结果存储。
5. **参数和验收：**召回数、重排、模型和并发值靠验证；关键行为的预期在验证前就要明确。不同能力不能只用一个综合正确率评价。

## 下一步建议

1. **先拿“计算上个月支付客户数”走通一次设计。**写清本次条件、要找到的依据、SQL 必须满足的规则、数据返回后的解释范围。用户不必先选择陌生的模型或数据库参数。
2. **同时核实数据平台适配器已有接口。**重点是身份如何传递、实际执行方言、提交请求/查询标识、状态恢复、取消、分页/截断、数据到齐依据，以及元数据稳定标识、分页与增量。未知项保留待核实。
3. **据此细化存储和 Rust 模块接口。**用现有六类知识组织所需规则和依赖，不先设计大而全的表结构。维护页按确有必要的信息补充。
4. **准备并开展有范围的小验证。**现有 20 题加少量端到端故障与数值反例；模型、向量服务和真实平台验证须先明确接入范围。当前仅完成资料核对。

多 Agent、图数据库、微服务拆分、大型语义计算引擎、微调、复杂归因、主动监控、长报告以及全表人工认证，均没有因本次审计成为 MVP 的前置要求。
