# 个人记忆：原方案与 Mem0 原始消息提取对比

## 范围和相同条件

A 为修复完整句来源边界后的原方案。B 在同一产品版本上用 Mem0 OSS 2.2.1 提取原始消息中的个人记忆并检索。两组使用同一 Pi SDK、DeepSeek Flash high、合成公共知识、用户输入和 Rust 的权限/版本/SQL 确认规则。产品只修复 `memory_source` 句尾与换行边界；Mem0 接缝只在独立实验目录。

B 的 Pi 仍判断是否值得长期保存、修订或停用，提供原文引用、适用范围和知识依赖。Mem0 收到完整原始用户消息和本次原文引用，不接收 Pi 编好的 name/body/scope。它的输出成为正式资产正文，再供 Agent 读取。这测量的是**受控记忆提取与复用**，不测任意聊天自动发现记忆，也不能概括 Mem0 全部能力。

## 写入与检索

1. 在正式工具登记前，用稳定的原 run_id/SDK tool_call_id 键调用 `memory.add(infer=True)`。每次提取使用独立 `run_id` 隔离暂存候选，避免失败候选混入下一次提取的历史。Mem0 2.2.1 是追加式提取，不能假定它自动更新旧资产。
2. 用 Mem0 输出替换工具 body；登记、执行和拒绝查询三条路径使用同一份参数。其他业务字段仍经 Rust 原入口校验。记录原参数与送入 Rust 的参数，便于独立核对。
3. Mem0 候选先处于 pending。Rust 保存成功后绑定正式 asset_id/version；修订替换旧绑定，停用撤销绑定。提交时使用锁定 SDK 的 vector_store.update 给候选增加 commit_state=ready 标记；检索在排序前过滤 commit_state=ready，避免暂存内容占满候选。每个提取操作只能绑定一条正式资产；只有已绑定且回源有效的候选可供采用。失败或未知不自动重传提取，同一 SDK 调用的登记、执行和拒绝查询命中持久回执。
4. MySQL 保留应用正式状态、来源和版本；Mem0 候选向量保存在独立 Milvus 集合，历史保存在独立 SQLite。搜索命中通过真实 Rust `read_knowledge` 登记权限/版本，使用已保存的 Mem0 正文。索引提交失败明确降级到正式资产目录，不声称 Mem0 成功。

## 固定实验和判分

9 个正常场景：跨对话、修订、临时覆盖、混合意图、停用、仅本次、金额单位、两个偏好、未核实纠错。另有 3 个故障场景：Mem0 预提取不可用、MySQL 正式保存失败、Mem0 索引提交失败。正常场景成功率和故障处理率分别报告；B 专属故障的 A 组是无故障参照，不混入优劣结论。

每场景每组固定两次，全新数据库/集合，两条轮次链并发运行，轮次内组顺序交替；每条链使用独立上下文，Agent 预算预留串行汇总所有活跃账本。共 48 个组合；失败、超时、缺回执不补抽，不修改题目求通过。重复次数用于观察波动，不把同题重复视为独立业务样本。记忆池仍最多两条，不测试大规模检索。

主指标为正常场景全部步骤正确数 / 18，附记忆持久化及管理成功、SQL 探针、运行完成率、成对差异、费用和延迟。SQL 按既有独立合成数据及变体执行核算，检查未确认状态、渠道和单位；文字、记忆的长期/临时范围及实际故障由未参与实现者独立复核。

机械评分只核对正式状态和独立 SQL，不能用 app/元 的子串作语义真值。临时覆盖检查原资产 ID、版本、正文、来源、范围完全不变，后续新对话继续采用原默认。语义正确性独立看正文，不以生成措辞修改答案。答案文件仅评分器可读，runner 只读取输入文件。

故障需要实际触发的独立证据：预提取故障必须有 Mem0 prepare 失败；保存故障必须有 SQLSTATE 45000；索引故障必须在 Rust 保存成功后触发。未到达注入点不能算通过。预提取失败不能伪装保存成功或偷偷回退 Pi 编写正文；之后新对话不能采用失败候选。

## 模型、预算和证据

向量模型沿用百炼 qwen3.7-text-embedding 1024 维。Mem0 提取使用 Flash，关闭思考、4096 输出 token、64KiB 请求体，无自动重试。每个组合 Agent 上限 48 次/US$1，每条消息 24 次；正式两轮合计上限 1100 次/US$20，提取 160 次/US$3，embedding 1000 次/¥2。未知预留计入总额；恢复只补从未开始的组合，不给旧失败补额。

先做独立 store 偏好小样，不进入正式分数。通过后冻结输入、答案、源码、模型配置，运行两轮。旧实验目录与结果保持；新结果不能与旧 7/11、4/11 直接当同版本提升率，也不改写 MVP 16 题历史成绩。
